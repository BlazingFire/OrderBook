# Design: Pending order numbering (rules 2 and 6), live presence (rule 3), stale-edit protection, and Master authority over every user's pending orders

> Written before the code (2026-10-01). Where it disagrees with docs/plans/1.3-BATCH-DETAIL.md, the integrated plan wins.

## Overview

The owner sees a human pending-order number such as PO/2026-27/00042 everywhere a pending order or its final order appears: list rows, detail headers, toasts, the lead PDF, order notes, search results, the dashboard and party detail. The Master mints the number inside createLead's existing transaction. That transaction already takes master_clock FOR UPDATE through nextHlc, and the number comes from an id_sequences row keyed 'po:2026-27', bumped with one UPDATE ... RETURNING. It is therefore serial, gap-free (a rollback undoes the bump) and unique, and a partial unique index on leads(tenant_id, po_number) backs that up. The financial year is worked out from the Master's clock in config.locale.timeZone (Asia/Kolkata), with the boundary at 00:00 on 1 April. A new add-only migration adds leads.po_number, back-numbers every existing lead (including soft-deleted ones) per financial year in (created_at, id) order using UPDATE only, and seeds the 'po:<fy>' counters past the backfill. A final order needs no copy of the number: the order query already LEFT JOINs leads as ld, so ld.po_number maps to Order.poNumber. One source of truth means the number cannot drift. On an Office panel a new pending order is still queued in the durable outbox, as today, so offline-first stays intact. When the link is up, POST /api/leads now waits up to 5 s for that mutation to settle (a per-mutationId waiter in office sync.service, resolved when the push response lands). It answers with permanentId and poNumber, so the toast reads 'Pending Order PO/2026-27/00042 saved'. When offline or on timeout it answers at once, the record shows a 'Provisional' pill, and on sync the Office emits an SSE 'numbered' event. That event moves an open provisional record to its permanent id and feeds the notification bell. On the Master, every applyPush now goes through one push gate that does two jobs. First, it serialises sync work, which removes the pool-starvation path where 10 panels each hold an advisory-lock connection while route() waits for more. Second, it uses group commit: pushes that arrive while one is being applied, or within a short window (default 150 ms, only when the push carries a create), are merged and sorted by HLC physical ms, then HLC counter, then device code, then the actor's username, then mutationId. Numbers already minted are never reshuffled, so strictly serial wins over timestamp order outside that window. For presence, each detail or edit screen on both panels sends a heartbeat every 10 s ({tabId, entity, id, mode: view|edit}). The Office sends it through POST /api/presence, which forwards a new 'presence:beat' socket command; the Master web uses a new POST /api/presence route. The Master keeps an in-memory presence store with a 30 s TTL. It checks visibility through getLead/getOrder on join, and on change pushes 'presence:changed' only to the connections that are on that record, re-gated with mayReceive. The Office relays that push over SSE. A shared AvatarStack in the EditorScreen header shows the other people on the record: an accent ring means editing, and a Server Master badge marks Server Master users. When someone else saves or deletes the record you have open, the push carries lastWrite {name, at, action}, and the edit form shows 'Ravi saved this at 10:42' with Reload theirs / Keep mine. Edits now send only the fields that changed, plus baseFieldHlc. The Office merge records a real conflict instead of silently overwriting, and the Master updateLead refuses a stale field with a 409 that the same banner handles. The Master's New Pending Order form gains an Owner picker (record.reassignOwner) so Server Master and admins can raise orders for any user. Delete already exists on the Master behind leads.delete plus party.accessAll.

## decisions

- The PO number is a separate column, leads.po_number. ENTITY_PREFIX, PERMANENT_ID_LENGTH and the LD/OD ids stay untouched, because id_map, FKs, isPermanentId and Phase K seeding depend on them.
- The counter is an id_sequences row with entity 'po:<fy>', not a Postgres SEQUENCE. id_sequences.entity is already TEXT and the row lock gives gap-free numbers. A new identity.repository nextInSeries() uses INSERT .. ON CONFLICT DO NOTHING followed by UPDATE .. RETURNING, so the first save of a new financial year cannot race on the insert.
- The financial year comes from the Master's own clock at the moment of minting, in config.locale.timeZone. That is the same instant as leads.created_at, so the number's year always matches the created date shown. An offline lead saved on 31 March and synced on 2 April is numbered in the new year, which matches its stored created_at.
- Format: PO/<yyyy>-<yy>/<seq padded to 5>. padStart never truncates, so a sixth digit just widens the number (CHECK ^PO/[0-9]{4}-[0-9]{2}/[0-9]{5,}$).
- No po_fy or po_seq columns. The financial year can be read from the string, and nothing sorts by sequence across years (YAGNI).
- Final orders read the number through the existing ld join (ld.po_number AS po_number). There is no orders.po_number column and no copy at convert, so there is a single source of truth. An order with no lead shows its OD id.
- The unique index covers soft-deleted leads too, so a deleted pending order's number is never reused.
- Only Master-minted numbers are real. An Office offline save keeps its temp id internally and shows 'Provisional' (with the temp id in the pill's title), never a guessed number.
- The online Office save waits for at most 5 s (OFFICE_SAVE_NUMBER_WAIT_MS) and never blocks offline. The outbox and temp id stay the source of truth. The existing un-deduped lead:create socket command is not used, because an ack timeout followed by a retry would create two leads.
- flush() in office sync.service gets a rerun flag. A submit that lands during an in-flight flush currently waits for the 5 s retry timer; with the flag it runs straight after the current flush.
- Cross-panel order: one process-wide push gate in master/src/services/push-gate.ts merges concurrent pushes. Sort key: HLC string, which is physical ms, then counter, then device code; then the actor's username; then mutationId. It sorts by HLC, which is monotonic per device, so each panel keeps its own enqueue order (party.create before lead.create).
- Gate window: 150 ms by default (MASTER_SYNC_ORDER_WINDOW_MS), applied only when the push contains a *.create; 0 turns it off. The test fixtures set it to 0 so existing suites stay fast.
- Pool starvation: fixed by serialising pushes rather than by raising pool.max. All writes already serialise on master_clock's row lock, so throughput is unchanged. The Office's sync:push ack timeout goes from 15 s to 60 s so a long serialised burst is not counted as an outage.
- Presence covers pending orders and final orders, in view and edit modes, on both panels. Other users only; your own userId is filtered out, and the same user across several tabs is merged into one avatar (edit wins).
- Presence is never stored in the DB, the change ring or activity_log. It is in-memory with a 10 s heartbeat and a 30 s TTL. It is cleared on panel socket disconnect, on auth assume/sign-out (onActorChanged), on admin socket disconnect (tabId in the handshake) and on pagehide (fetch keepalive).
- Presence fan-out goes only to the connections currently on that record, each re-checked with actorForRecipient and mayReceive. Visibility is checked once on join with getLead/getOrder, so presence can never reveal a lead on a party the person may not see.
- The Master web posts presence over HTTP (POST /api/presence) instead of adding the first admin-socket command, which keeps the rule that admin sockets only listen.
- lastWrite (who saved or deleted) comes from two new optional fields on DataChangedEvent, actorUserId and actorName. They are stamped by the lead and order publishers and by the sync republish. There is no updated_by column.
- Stale-edit protection is one idea on both panels: send only the changed fields, plus baseFieldHlc for them. The Office merge then records a real sync_conflict. The Master updateLead/updateOrder answer 409 error.conflict.staleEdit when a sent field's stored HLC differs from its base. 'Keep mine' resends with the current fieldHlc as base. The existing ConflictNotice (Reload/Overwrite) UI is reused.
- sameLines/lineKey move from master sync.service.ts to shared/src/sync/merge.ts. Clients then send items only when the lines really changed, so an untouched line set never clobbers someone else's line edit.
- The Owner picker is on the Master entry form only. buildLeadEntryView returns owners[] only when the actor has record.reassignOwner. The Office form is unchanged.
- No new permission keys. Presence uses leads.view/orders.view plus party scope. On-behalf creation uses record.reassignOwner. Delete-any uses leads.delete plus party.accessAll, which the roles domain must grant to Server Master.
- A provisional record gets no presence beat. Temp ids are never sent to the Master for presence.
- PDF filename: pending-order-PO-2026-27-00042.pdf (slashes replaced). The URL stays /api/leads/:id/pdf, so the Electron isLeadPdfUrl allowlist is unchanged.
- The order list's primary number column shows the PO number. The OD id moves to a secondary small mono column ('Order ref'), replacing the old leadId column.

## dataModel

- 20261002000000_pending_order_numbers (master/src/db/migrations/20261002000000_pending_order_numbers.ts), additive only. (1) ALTER TABLE leads ADD COLUMN IF NOT EXISTS po_number TEXT NULL CONSTRAINT leads_po_number_format CHECK (po_number ~ '^PO/[0-9]{4}-[0-9]{2}/[0-9]{5,}$'). (2) Backfill with UPDATE only: WITH src AS (SELECT id, tenant_id, created_at, CASE WHEN EXTRACT(MONTH FROM created_at AT TIME ZONE :tz) >= 4 THEN EXTRACT(YEAR FROM created_at AT TIME ZONE :tz) ELSE EXTRACT(YEAR FROM created_at AT TIME ZONE :tz) - 1 END::int AS fy0 FROM leads WHERE po_number IS NULL), labelled AS (SELECT *, fy0 || '-' || lpad(((fy0+1) % 100)::text, 2, '0') AS fy FROM src), base AS (SELECT tenant_id, split_part(po_number,'/',2) AS fy, max(split_part(po_number,'/',3)::bigint) AS top FROM leads WHERE po_number IS NOT NULL GROUP BY 1,2), numbered AS (SELECT l.id, l.fy, coalesce(b.top,0) + row_number() OVER (PARTITION BY l.tenant_id, l.fy ORDER BY l.created_at, l.id) AS n FROM labelled l LEFT JOIN base b USING (tenant_id, fy)) UPDATE leads SET po_number = 'PO/' || numbered.fy || '/' || lpad(n::text, greatest(5, length(n::text)), '0') FROM numbered WHERE leads.id = numbered.id. This includes soft-deleted leads and is idempotent: a re-run only numbers rows that are still NULL and continues after the existing maximum. tz = process.env.ORDERBOOK_TIMEZONE || 'Asia/Kolkata', frozen in the file and matching master/src/config/index.ts:143. (3) CREATE UNIQUE INDEX IF NOT EXISTS leads_po_number_uq ON leads (tenant_id, po_number) WHERE po_number IS NOT NULL. (4) Seed counters: INSERT INTO id_sequences (tenant_id, entity, next_value) SELECT tenant_id, 'po:' || split_part(po_number,'/',2), max(split_part(po_number,'/',3)::bigint) + 1 FROM leads WHERE po_number IS NOT NULL GROUP BY 1,2 ON CONFLICT (tenant_id, entity) DO UPDATE SET next_value = greatest(id_sequences.next_value, EXCLUDED.next_value). down() drops the index and the column (allowed in down only).
- Registry: append { name: '20261002000000_pending_order_numbers', ...pendingOrderNumbers } at the end of master/src/db/migrations/index.ts and add the name to DELIBERATELY_LAST in master/tests/migration-registry.test.ts, after '20260401000000_order_vehicle_number'. The timestamp has to be coordinated with sibling-domain migrations so the non-pinned order stays ascending.
- No new tables. The presence state is in-memory only (master/src/realtime/presence-store.ts).
- id_sequences gains rows keyed 'po:<fy>' at runtime, created lazily by nextInSeries on the first save of a financial year. master/src/services/catalog-reload-cli.ts's erase loop must also reset them: add trx('id_sequences').where({tenant_id}).andWhereLike('entity','po:%').update({next_value: 1}). The test fixture resetData already resets every id_sequences row.

## permissions

- No new permission keys and no grant migration.
- Presence join: leads.view (entity lead) or orders.view (entity order), plus party scope. It is enforced by calling leadService.getLead / orderService.getOrder on join, and re-gated per recipient with fan-out.ts mayReceive.
- Owner picker and create-on-behalf: the existing record.reassignOwner (MINIMUM_TIER management). The picker is rendered only when the Master's GET /api/lead-entry returns owners[], which it does only for actors that hold it.
- Delete any user's pending order: the existing leads.delete together with party.accessAll (an unrestricted Master delete). The roles domain must grant both, plus record.reassignOwner, leads.*, orders.*, to the new Server Master tier and keep them on Normal Admin.

### 4. Master push gate: serialise, group-commit, HLC order

Files: `master/src/services/push-gate.ts`, `master/src/services/sync.service.ts`, `master/src/config/index.ts`, `master/tests/helpers/fixtures.ts`

push-gate.ts: a module-level queue of {request, actor, resolve, reject} and one draining promise chain. When an entry arrives and the gate is idle, wait windowMs only if any mutation kind ends in '.create', otherwise drain on the next tick. The drain takes every queued entry and runs the existing signInToSync 503 check per entry (that entry rejects alone). It flattens to {mutation, entryIndex}, sorts with compareForIdAssignment({...m, actorName: actor.actorName}), and applies sequentially through sync.service's applyOne with the per-entry alreadyApplied map. A retryable throw rejects only that entry and skips its remaining mutations; already-applied ones replay as duplicates on retry. Each entry is resolved with its own results, idMappings (listIdMappings) and serverHlc. sync.service.applyPush becomes `return runPush(request, actor)`; the existing body becomes applyPushGroup and is exported for the gate. route() 'lead.create' returns {...applied(mutation, lead.id), number: lead.poNumber ?? undefined}. mergeUpdate's republish passes the actor stamp. Rewrite the header comment (L6-8) to describe the gate. Add config sync.orderWindowMs. fixtures.setupDatabase calls configurePushGate({windowMs: 0}).

## risks

- Gate latency: serialising all pushes means a large reconnect burst (10 panels x 100 mutations) waits in line. Throughput is unchanged because master_clock already serialises every write, but individual acks get slower. That is why the Office sync:push ack timeout is raised to 60 s. A timed-out push is retried and replays as 'duplicate', so nothing is lost, only noisy.
- The cross-panel timestamp order holds only inside the arrival window or while a previous group is applying. A panel that reconnects later gets later numbers even if its HLC is older. This is the deliberate ceiling of 'strictly serial, never reused' and must be documented for the owner.
- Clock skew: HLC physical time comes from each Office PC's wall clock, so a PC whose clock runs fast wins ordering ties inside the window. Numbers stay unique and gap-free; only the relative order is affected.
- Sample-data removal or any hard delete of leads leaves holes in the series, because numbers are never reused. That is acceptable for demo data and must be documented.
- Backfill TZ: the migration reads ORDERBOOK_TIMEZONE at run time. If an install changes timezone later, old numbers keep their original FY. The default 'Asia/Kolkata' mirrors config.
- The two lead UIs (office/web AddLeadScreen + LeadDetail vs ui LeadEntryScreen + LeadRecordView) must both get the changed-field diff, baseFieldHlc, RecordNumber and the stale banner, or behaviour diverges between panels.
- Sending only changed fields changes what an Office lead.update payload carries. local-store pickLeadFields must keep fields that are absent untouched (verify it does not reset missing keys). Old Masters still accept partial payloads because mergeUpdate filters by fields.
- Presence fan-out re-resolves the actor per recipient (one query for admin sockets). It is bounded because recipients are only the people on that record and changes are debounced. Heartbeats never broadcast.
- Office SSE has no replay, so a presence frame missed during a reconnect self-heals on the next 10 s beat, whose ack returns the full viewer list.
- The Office server's POST /api/leads now holds the HTTP request for up to 5 s while online. The browser Save button must show the numbering state, and a double-click is already guarded by saving.current.
- Mixed versions: an old Office ignores poNumber and presence (it shows LD ids and no avatars). An old Master returns no number (the Office shows the permanent id), and 'presence:beat' times out after 15 s (the hook ignores the error, but this is a wasted command every 10 s). Mitigation: stop beating after the first unavailable/timeout until the next reconnect. Ship the Master and Office together.
- applied_mutations must store the full result JSON for result.number to replay. Verify syncRepo.recordAppliedMutation persists unknown keys (if it whitelists columns, add number to it).
- Server Master tier naming ('server_master') and role grants come from the roles domain. Until it lands, the badge simply never renders.
