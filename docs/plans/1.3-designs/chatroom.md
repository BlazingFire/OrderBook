# Design: Chatroom (+ chat extras: @mentions, unread badges, search, 5-min edit/delete, tasks with read receipts, pins, announcement groups, record chips)

> Written before the code (2026-10-01). Where it disagrees with docs/plans/1.3-BATCH-DETAIL.md, the integrated plan wins.

## Overview

The owner gets a Chatroom entry in the sidebar of both panels, plus a Basic Home tile. It shows a total unread badge and folds three sub-pages: Rooms, My tasks and Groups (Groups only for chat.createGroups / chat.manage). Rooms lists the user's groups and direct chats, newest activity first. Each row has its own unread badge, an @-mention dot and a last-message preview, and a search box across every room the user belongs to. Opening a room is a sub-screen with a back button and a nested sidebar entry carrying the room name (useSubNav, as LeadBoardScreen does). It has a pinned bar, a message list with day separators that pages 50 at a time with "Load older", task cards, and a composer with @mention autocomplete, a record picker and a 'make task' toggle. A record chip is a pending order or final order, labelled by its PO number. Clicking a chip calls the shell's existing openRecord path. The receiving panel opens the record natively, and the Office fetches it from the Master when it is not in its 500-row local view. If the record is restricted or gone, the user gets the existing nav.recordNotAvailable toast. Chat is text only. Bodies render as plain text with no auto-linking, there are no files or images, the limit is 4000 characters and a message holds at most 5 record refs. On the Master, chat lives in three new tables: chat_rooms, chat_members (role admin/member, muted, last_read_seq) and chat_messages. A message has a per-room gap-free seq allocated under the room row lock, and tasks, pins and tombstones are columns on chat_messages, not extra tables. Read receipts on tasks are derived from members' last_read_seq, so no receipt table is needed. Master web writes over a new /api/chat REST router. Office panels use twinned socket commands (chat:*) that office/src/http/app.ts forwards at the same paths. Posting from an Office goes through the existing durable outbox as a new 'chat.post' mutation kind, which gives offline queueing, idempotency (mutationId → applied_mutations, client_id) and auto-send on reconnect for free. The bubble shows 'Sending…' until the Master's push arrives with the matching clientId. Live updates bypass the change ring and the activity chain completely. chat.service publishes a ChatPush through a new publishChat/onChat pair in change-bus.ts (beside publishConflict). hub.ts sends one Server→Client event, 'chat:event', only to sockets whose current actor is a room member holding chat.use. The Office relays it into its SSE stream as event type 'chat', and on every reconnect it re-fetches, because SSE has no replay. Only governance actions are audited through recordActivity: room create/update/archive, member changes, pins and a moderator's removal of someone else's message. Ordinary posts, edits, reads and task ticks are not. Permissions are six capabilities in a new 'chat' group. A grant migration hands them to admin-tier (and server_master-tier) roles. Office and management roles get them only when an admin ticks them in the role editor. With nothing granted the feature is invisible, so no company setting is needed.

## decisions

- Office posts go through the existing outbox as MUTATION_KIND 'chat.post' (entity 'chat_message'), not a separate chat outbox. This reuses durable queueing, flush-on-reconnect, applied_mutations idempotency and the refusals screen with no new storage.
- Reading needs the Master. If a re-fetch fails with 503, the Office browser keeps whatever messages it already holds and shows an OfflineBanner ('chat.offline'). The composer stays enabled because it queues. The Office server keeps no chat cache: no disk cache and no in-memory cache. ponytail: if owners ask to read history fully offline, add a per-room ring cache in office/src.
- The Master's sync route 'chat.post' refuses a mutation whose actorUserId differs from the pushing socket's acting user (validation.chat.wrongAuthor). Without this, a message queued by A and flushed after B signs in on that panel would post as B.
- chat_messages.id uses the permanent-id scheme ('CM' + 10 digits via allocatePermanentId) because outbox envelopes require a SyncableEntity and temp→permanent mapping. chat_rooms.id is a UUID (gen_random_uuid()), because rooms are never created offline.
- Ordering and unread counts use a per-room seq: chat_rooms.last_seq is bumped under SELECT … FOR UPDATE in the insert transaction, which keeps it gap-free. The author's last_read_seq is advanced in the same transaction, so unread = last_seq - last_read_seq with no COUNT query.
- Tasks are columns on chat_messages (kind='task', task_assignees JSONB, task_due_on, task_done_at/by) rather than a chat_tasks table. There is one shared done state per task. An assignee, the task's author, a room admin or a chat.manage holder may tick or untick it.
- Read receipts on tasks are derived: member X has seen a task when X.last_read_seq >= task.seq. The room detail carries members' lastReadSeq, and 'read' pushes update it live. No receipt table.
- Room member roles are 'admin' and 'member' only. The creator becomes admin, and there is no separate 'owner' role. Announcement mode is a flag (announce_only) on a group rather than a third room kind, so it can be toggled. Room kinds are 'group' and 'direct'.
- A direct chat is find-or-create on a unique (tenant_id, direct_key = sorted user ids). The initiator needs chat.directMessages. The other person only needs chat.use to read and reply.
- chat.manage holders (admin tier) can list and administer every group, including members, announce mode, archive, pins and moderation deletes. To read a group's messages they must add themselves, which is audited. DMs are never visible to anyone outside the pair.
- Deletion is a tombstone: deleted_at/deleted_by are set and the pin is cleared. The body stays in the database for audit but the mapper never serves it, so clients show 'Message deleted'. Messages are not in the Recycle Bin, there is no purge, and they are kept forever.
- Edit and delete of your own message are allowed within 5 minutes, enforced server-side against DB now(). After that, deletion is for room admins and chat.manage only, and is audited as activity.chat_message.removed. Edits keep no history.
- Record chips store only {type:'lead'|'order', id, label}. The label is the PO number (from the numbering domain), falling back to the id. No party name is stored, so a chip never leaks a restricted party's name to a room member. The sender must be able to open the record: the server checks it through leadService.getLead / orderService.getOrder with the sender's actor after identityRepo.resolveId, which also resolves offline temp ids.
- Chips open through a callback prop (onOpenRecord) into each shell's existing openRecord path rather than through new #/lead/<id> hash routes. The Master already has openRecord plus a fallback fetch, so the Office just gets the same fallback. This needs less code and no hash parser.
- Low-RAM handling uses native features rather than a virtualization library. Pages are 50 messages, at most 300 are held per open room (the oldest are dropped and refetched via 'Load older'), and rows use CSS content-visibility:auto with contain-intrinsic-size (Chromium 85+, so it works in the Win7 Chromium 108 build). Avatars are size 'xs'.
- There is one Server→Client event, 'chat:event', with a small union payload: 'message' (upsert, which also covers edit, delete, pin and task tick), 'room' (refetch rooms and detail) and 'read'. A single event means fewer contract entries, one Office relay and one SSE type. 'room' carries only an id because summaries differ per viewer.
- The nav unread total is refreshed by re-fetching the room list, debounced 400 ms after any push or on resync, rather than by incremental client arithmetic. Muted rooms are excluded from the nav total but still badge in the list.
- Group names are unique per tenant among live groups (case-insensitive partial unique index). A clash raises ConflictError 'conflict.chat.roomName'.
- System messages (kind='system', with a system JSONB {event, params}) record created, memberAdded, memberRemoved, renamed, announceOn/off, archived and unarchived in the room timeline. They are rendered through an explicit event→key map, not a template literal, so i18n-call-sites can see the keys.
- Audit scope is governance only. Recorded: chat_room created/updated/archived/restored/memberAdded/memberRemoved/roleChanged, and chat_message removed (by a moderator)/pinned/unpinned. Not recorded: posts, own edits or deletes, reads, mutes, task ticks. This keeps chat off the per-tenant activity-chain advisory lock.
- There is no company setting or CompanyFeatures flag. Permissions are the switch, and a fresh role holds none.
- wipe:business (catalog-reload-cli.ts) also truncates the three chat tables and resets the 'chat_message' id_sequence. Otherwise chips would point at LD/OD ids that get reused after a wipe.
- ROLE_TEMPLATES (templates, not seeded rows): Sales gets chat.use, chat.directMessages, chat.shareRecords and chat.tasks; Dispatch gets chat.use. Templates are offered when creating a role, so this hands nobody anything automatically.
- Message search uses ILIKE over the user's member rooms only, needs at least 2 characters, returns the newest 50 and excludes tombstones. ponytail: no pg_trgm index until a profile says so. Clicking a hit opens the room with beforeSeq = hit.seq + 26 so the hit is on the loaded page, and highlights it.

## dataModel

- 20261005000000_chatroom.ts (additive, IF NOT EXISTS throughout; down() drops the three tables). CREATE TABLE chat_rooms (id UUID PK DEFAULT gen_random_uuid(), tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE, kind TEXT NOT NULL CHECK (kind IN ('group','direct')), name TEXT NULL CHECK (kind='direct' OR char_length(btrim(name)) BETWEEN 1 AND 60), description TEXT NULL CHECK (description IS NULL OR char_length(description) <= 280), announce_only BOOLEAN NOT NULL DEFAULT false, direct_key TEXT NULL, last_seq BIGINT NOT NULL DEFAULT 0, last_message_at TIMESTAMPTZ NULL, created_by TEXT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now(), updated_at TIMESTAMPTZ NOT NULL DEFAULT now(), archived_at TIMESTAMPTZ NULL, archived_by TEXT NULL); UNIQUE INDEX chat_rooms_direct_key_uq ON (tenant_id, direct_key) WHERE direct_key IS NOT NULL; UNIQUE INDEX chat_rooms_group_name_uq ON (tenant_id, lower(name)) WHERE kind='group' AND archived_at IS NULL; INDEX chat_rooms_recent_idx ON (tenant_id, last_message_at DESC). User ids are TEXT with no FK, following the party_access.user_id / api_keys.owner_user_id convention, because users are soft-deleted and restorable.
- Same migration: CREATE TABLE chat_members (room_id UUID NOT NULL REFERENCES chat_rooms(id) ON DELETE CASCADE, tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE, user_id TEXT NOT NULL, role TEXT NOT NULL DEFAULT 'member' CHECK (role IN ('admin','member')), muted BOOLEAN NOT NULL DEFAULT false, last_read_seq BIGINT NOT NULL DEFAULT 0, joined_at TIMESTAMPTZ NOT NULL DEFAULT now(), PRIMARY KEY (room_id, user_id)); INDEX chat_members_user_idx ON (tenant_id, user_id). tenant_id is carried so backup 'selected' scope works without a TRANSITIVELY_SCOPED entry.
- Same migration: CREATE TABLE chat_messages (id TEXT PK CHECK (id ~ '^CM[0-9]{10}$'), tenant_id UUID NOT NULL REFERENCES tenants(id) ON DELETE CASCADE, room_id UUID NOT NULL REFERENCES chat_rooms(id) ON DELETE CASCADE, seq BIGINT NOT NULL, author_id TEXT NULL, kind TEXT NOT NULL CHECK (kind IN ('text','task','system')), body TEXT NOT NULL DEFAULT '' CHECK (char_length(body) <= 4000), refs JSONB NOT NULL DEFAULT '[]', mentions JSONB NOT NULL DEFAULT '[]', system JSONB NULL, client_id TEXT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT now(), edited_at TIMESTAMPTZ NULL, deleted_at TIMESTAMPTZ NULL, deleted_by TEXT NULL, pinned_at TIMESTAMPTZ NULL, pinned_by TEXT NULL, task_assignees JSONB NULL, task_due_on DATE NULL, task_done_at TIMESTAMPTZ NULL, task_done_by TEXT NULL, CHECK (kind='task' OR task_assignees IS NULL)); UNIQUE (room_id, seq); UNIQUE INDEX chat_messages_client_uq ON (tenant_id, client_id) WHERE client_id IS NOT NULL; INDEX chat_messages_room_seq_idx ON (room_id, seq DESC); INDEX chat_messages_pinned_idx ON (room_id) WHERE pinned_at IS NOT NULL; INDEX chat_messages_open_tasks_idx ON (tenant_id) WHERE kind='task' AND task_done_at IS NULL AND deleted_at IS NULL.
- No id_sequences seed: allocatePermanentId inserts the 'chat_message' row lazily (identity.repository.ts).
- 20261005000100_chat_permission_grant.ts is a copy of 20260319000000_products_bulk_permission_grant.ts. Frozen NEW_KEYS = ['chat.use','chat.directMessages','chat.shareRecords','chat.tasks','chat.createGroups','chat.manage'] and frozen TIERS = ['admin','server_master'] (whereIn tier). The 'server_master' entry matches nothing until the roles domain's tier migration exists, which keeps it order-independent. It does a union + sort with no tenant or deleted filter, and down() is empty. It never imports PERMISSIONS live.
- Both names are appended to master/src/db/migrations/index.ts and to the tail of DELIBERATELY_LAST in master/tests/migration-registry.test.ts. The final timestamps are coordinated with the other domains' migrations in this batch. Neither migration has a backfill: chat is new.

## permissions

- chat.use (capability, group 'chat', no MINIMUM_TIER → office): see the Chatroom, read and post in rooms you belong to, edit or delete your own messages within 5 minutes, tick tasks assigned to you, mute, leave a group, and search your rooms. Also the MUTATION_PERMISSIONS entry for 'chat.post' and the needs() on every /api/chat route.
- chat.directMessages (office): start a 1:1 chat with any active chat user.
- chat.shareRecords (office): attach pending order / final order chips. The server also checks that the sender can open each referenced record (leads.view/orders.view + party scope).
- chat.tasks (office): post a message as a task and assign it to room members.
- chat.createGroups (MINIMUM_TIER management): create groups. The creator becomes the room admin, and room admins can pin, toggle announce-only, archive, rename, manage members and moderate within their own rooms.
- chat.manage (MINIMUM_TIER admin): administer every group company-wide (list all groups, membership, pins, announce mode, archive, moderation deletes) without being a room admin.
- Grant: migration 20261005000100 gives all six to admin and server_master tier roles (union). On a fresh install the Administrator also gets them through 20260303's live allPermissions(). Management and office roles get them only when an admin ticks them in PermissionGrid (rendered automatically from the new CAPABILITY_GROUPS entry 'chat').
- UI gates: the Chatroom nav, tile and screen need chat.use. 'New direct chat' needs chat.directMessages. The record-picker button needs chat.shareRecords. The 'Task' toggle needs chat.tasks. 'New group' needs chat.createGroups or chat.manage. The Groups sub-page needs chat.createGroups or chat.manage. Controls a role lacks are absent, not disabled. The composer is absent in announce-only rooms for anyone who is not a room admin or chat.manage holder.

## interfaces

- Master REST, new router master/src/http/routes/chat.routes.ts mounted app.use('/api/chat', chatRoutes) before app.use('/api', dataRoutes). Every handler has needs('chat.use'), and the service enforces the finer keys. Routes: GET /people → ChatPerson[]; GET /rooms?all=1 → ChatRoomSummary[]; POST /rooms (ChatRoomInput) → ChatRoomSummary; GET /rooms/:id → ChatRoomDetail; PUT /rooms/:id (ChatRoomPatch {name?, description?, announceOnly?, archived?}) → ChatRoomSummary; POST /rooms/:id/members ({userId, role:'admin'|'member'|null}) → ChatRoomDetail; GET /rooms/:id/messages?before=&limit= → ChatMessage[]; POST /rooms/:id/messages (ChatPostInput) → ChatMessage; POST /rooms/:id/read ({seq}) → {lastReadSeq}; POST /rooms/:id/mute ({muted}) → null; POST /direct ({userId}) → ChatRoomSummary; PUT /messages/:id ({body, mentions?}) → ChatMessage; DELETE /messages/:id → ChatMessage; POST /messages/:id/pin ({pinned}) → ChatMessage; POST /messages/:id/done ({done}) → ChatMessage; GET /search?q=&roomId= → ChatSearchHit[]; GET /tasks?scope=mine|created&includeDone=1 → ChatTaskRow[].
- ClientToServerEvents (panel socket, registered in hub.ts registerCommands via run(ack, actor => chatService.x(...))): 'chat:people' (ack); 'chat:rooms' ({all?}, ack); 'chat:room' (roomId, ack); 'chat:messages' ({roomId, beforeSeq?, limit?}, ack); 'chat:search' ({q, roomId?}, ack); 'chat:tasks' ({scope, includeDone?}, ack); 'chat:roomCreate' (ChatRoomInput, ack); 'chat:roomUpdate' ({roomId, input}, ack); 'chat:memberSet' ({roomId, userId, role}, ack); 'chat:direct' ({userId}, ack); 'chat:edit' ({messageId, body, mentions?}, ack); 'chat:delete' (messageId, ack); 'chat:pin' ({messageId, pinned}, ack); 'chat:taskDone' ({messageId, done}, ack); 'chat:read' ({roomId, seq}, ack); 'chat:mute' ({roomId, muted}, ack). There is deliberately no 'chat:post' socket command: Office posts travel in sync:push as 'chat.post' mutations.
- ServerToClientEvents: 'chat:event' (push: ChatPush). It is emitted in hub.ts (onChat → emitChatToMembers) and handled in office/src/realtime/master-connection.ts (socket.on('chat:event') → this.emit('chat', push)), which satisfies socket-contract.test.ts with no masterBrowserOnly entry. ChatPush = {kind:'message', roomId, message: ChatMessage} | {kind:'room', roomId} | {kind:'read', roomId, userId, seq}.
- Mutation: MUTATION_KINDS += 'chat.post'; MUTATION_PERMISSIONS['chat.post'] = 'chat.use'; SYNCABLE_ENTITIES += 'chat_message' with ENTITY_PREFIX 'CM'. payload = {roomId, body, refs?, mentions?, task?}. Master sync.service route(): case 'chat.post' → wrong-author check → chatService.postMessage(roomId, {...payload, clientId: mutation.mutationId}, actor) → mapTemporaryId → applied(mutation, message.id).
- Office server (office/src/http/app.ts, after requireUser): the same /api/chat/* paths. GETs, PUT and DELETE use forward(res, 'chat:…', …). POST /api/chat/rooms/:id/messages uses queue({kind:'chat.post', entity:'chat_message', payload:{roomId, …}, validate: () => chatPostProblem(payload)}) → 202 {queued, id, mutationId}. GET /api/chat/rooms/:id/messages forwards and then appends this panel's still-queued chat.post outbox entries for that room as ChatMessage-shaped {pending:true, clientId: mutationId}. On 503, it returns 503 together with the pending list in the body. New GET /api/leads/:id and GET /api/orders/:id return the local view first (forCurrentUser), otherwise forward('lead:get'|'order:get', id). These are the existing Master commands that had no Office caller.
- Office SSE: masterConnection.on('chat', push => broadcast('chat', push)). This adds event type 'chat' beside status, snapshot, change and conflict.
- In-process bus: master/src/services/change-bus.ts adds publishChat(event: {tenantId, userIds: string[], push: ChatPush}) and onChat(listener). It never touches change-ring.
- Wire types (new file shared/src/domain/chat.ts, exported from the shared index): ChatRoomKind, ChatMemberRole, ChatRef {type:'lead'|'order', id, label}, ChatPerson {id, displayName, avatar, tier}, ChatMessage {id, roomId, seq, kind, author: ChatPerson|null, body, refs, mentions, system?, createdAt, editedAt, deletedAt, pinnedAt, pinnedBy, task?: {assignees, dueOn, doneAt, doneBy}, clientId, pending?}, ChatRoomSummary {id, kind, name, description, announceOnly, archivedAt, myRole|null, muted, lastSeq, lastReadSeq, unread, mentionUnread, memberCount, lastMessage?, direct?: ChatPerson}, ChatRoomDetail (summary + members[{…ChatPerson, role, lastReadSeq}] + pinned: ChatMessage[]), ChatPostInput, ChatRoomInput, ChatRoomPatch, ChatSearchHit, ChatTaskRow, ChatPush, CHAT_LIMITS {bodyMax:4000, refsMax:5, mentionsMax:20, nameMax:60, descriptionMax:280, editWindowMs:300000, pageSize:50, keepInMemory:300}, and pure helpers cleanChatPost(input) → {value}|{errorKey: MessageKey}, withinEditWindow(createdAt, now), unreadOf(summary). All fields optional on the wire where they ride existing types (none do; chat types are new).

## settings

- None. No SETTINGS entry and no CompanyFeatures field: the six chat permissions are the on/off switch, and a company where nobody holds chat.use shows no Chatroom anywhere. The limits (4000 characters, 5-minute edit window, page of 50) are owner-fixed constants in CHAT_LIMITS, not settings.

## risks

- Fan-out cost: every chat push resolves an actor per connected socket (DB query). With 10 panels plus a few Master browsers and 'read' pushes on every read, that is tens of small queries per message. Acceptable on a LAN at this scale; the upgrade path is a per-socket userId cache, marked ponytail.
- Pool pressure: an Office 'chat.post' runs inside applyOne's held outer connection, plus the postMessage transaction, plus ref validation reads. This adds to the known pool-of-10 starvation risk (map 1). Ref validation runs before the transaction to keep lock hold short. The pool fix belongs to the numbering/sync domain.
- Outbox coupling: a retryable failure of an earlier lead mutation blocks chat posts queued behind it in the same flush, and chat posts add to the 'syncing N' counter. This is intended, but should be documented.
- Version skew: an old Master never grants chat.use, so new Offices hide Chatroom (safe). A new Master with an old Office: the panel ignores 'chat:event' and never shows chat (safe). A new Office calling chat:* on an old Master would wait 15 s and get a 503, which only happens if chat.use somehow exists, so the risk is low.
- Party-scope leak avoided by storing only the PO label on chips. If the numbering domain changes the label to include the party name, this must be revisited.
- SSE has no replay. Pushes during an Office server restart or a tab reconnect are lost, mitigated by resync on 'open'/'connected'. A missed 'read' push only leaves receipts stale until the next re-fetch.
- Win7 legacy build (Chromium 108 / Node 16): avoid post-108 JS/CSS (toSorted, Object.groupBy, CSS nesting, :has is fine) in the ui chat files. Node 16 on the Office server is unaffected by the trivial forwarding code.
- Nav churn: adding 'chat' to MASTER_NAV/OFFICE_NAV collides with the Basic Home, Printroom and Inventory-removal nav changes. It must land in the same coordinated change as the shells domain or keys-nav-order and the shell tests break.
- i18n volume: about 95 new keys. The activity token lock is append-only, so token names must be final before the first commit.
- Lock ordering: postMessage takes the chat_rooms row lock and then the id_sequences 'chat_message' row lock. No other path takes them in reverse; keep it that way in future edits.
