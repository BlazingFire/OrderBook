# 09 — The translation layer

Status: **specified, nothing built.** Part of the backend build plan in `docs/BACKEND_MODULES.md`;
this document is the full specification of §4 of that plan.

Scope: English and Hindi, both panels, every string a person reads. The owner overruled the
recommendation in `docs/UI_REDESIGN.md` §4.4 to defer this. **It ships**, and it ships **first** —
`AppError`'s constructor signature is a dependency of the other five modules, so every hour this
module is late is an hour of throw sites written twice.

This is also the cheapest of the six modules, for a reason worth stating up front: the token
contract already exists in the codebase and is load-bearing. What is missing is the catalogue, `t()`,
and a picker.

---

## 1. The groundwork that already exists

`docs/UI_REDESIGN.md` §4.4 sized this module as a sweep of every literal across ~4,000 lines of JSX,
on the strength of `HANDOFF.md` calling the layer "not built". That estimate is wrong, and the
evidence is in three files.

### 1.1 Every permission catalogue entry already carries a token

`shared/src/domain/permissions.ts:82-87` — the comment is the contract:

```ts
interface CapabilityDefinition {
  key: string;
  group: CapabilityGroup;
  /** Translation token; the renderer never hard-codes the English. */
  labelToken: string;
}
```

All twelve capabilities supply one (`permissions.ts:89-113`), for example
`{ key: 'lead.convert', group: 'workflow', labelToken: 'permission.lead.convert' }` at
`permissions.ts:90`. The served catalogue mints two more families —
`labelToken: \`module.${module}\`` (`permissions.ts:341`) and
`labelToken: \`capabilityGroup.${group}\`` (`permissions.ts:347`) — and the file header states the
purpose plainly: *"a new capability reaches the screen with one translation entry and no UI change"*
(`permissions.ts:19-21`).

`ROLE_TEMPLATES` does the same with `nameToken` (`permissions.ts:241`), spent at
`permissions.ts:246` (`'roleTemplate.sales'`) and `permissions.ts:268` (`'roleTemplate.dispatch'`).

**Twenty-five tokens exist today and not one of them resolves to anything.** There is no catalogue
to look them up in. The renderer that was supposed to consume them
(`master/web/src/components/PermissionGrid.tsx`) ignores every one and prints raw keys or a local
humaniser instead — see §6.4. That is the gap this module closes; the contract itself is already
designed and already correct.

### 1.2 The audit trail already stores tokens plus params, not sentences

`master/src/repositories/activity-log.repository.ts:34-42`:

```ts
export interface ActivityEntry {
  tenantId: string;
  entityType: string;
  entityId: string;
  action: string;
  actorType: ActorType;
  actorId: string | null;
  details?: Record<string, unknown>;
}
```

No column holds prose. `(entity_type, action)` is a token pair and `details` is a JSONB parameter
bag. A row written in March renders in Hindi in September with no schema change, no backfill, and no
rewrite of the hash chain — see §3.2.

### 1.3 The error envelope already carries structured facts

`AppError` already has `code` and `details` (`master/src/lib/errors.ts:7-28`), the HTTP transport
already emits them (`master/src/http/middleware/error-handler.ts:28-32`), and the browser client
already models them (`master/web/src/api.ts:41-67`). This module adds two optional fields to a shape
that is already the right shape. It does not invent an envelope.

### 1.4 What is genuinely absent

| Absent | Consequence today |
|---|---|
| `shared/src/i18n/` | The 25 `labelToken` values resolve to nothing |
| `t()` | Every user-facing string is a JSX literal |
| A `Locale` type, a picker, per-machine storage | There is no way to ask for Hindi |
| A Devanagari-capable font stack | `font-family: 'Segoe UI', Tahoma, Arial, sans-serif` (`master/web/src/styles.css:26`, `office/web/src/styles.css:26`) renders Devanagari as tofu |
| A token on `AppError` | Every server-originated message is English prose |

## 2. The central decision

> **The server never renders a user-facing sentence.** It returns a stable `messageKey` plus named
> params, and the client renders.

Every other decision in this document falls out of that one.

### 2.1 It is forced, not chosen

Locale is **per-machine and never synced** — the same rule the design spec applies to theme and
density (`docs/UI_REDESIGN.md:130`, *"per-machine, never synced"*). That is not a preference; it is
what the deployment is. One Master serves several Office Panels on a LAN. When the Master refuses a
command, it is answering a socket, not a person: `hub.ts` `respond()`
(`master/src/realtime/hub.ts:391-406`) has an `ack` callback and an `ActorContext`, and neither
carries a language.

Three alternatives were considered and each fails on the same fact:

| Alternative | Why it fails |
|---|---|
| Send the locale up with each command | The Master would render for whichever browser happened to send the command — but the same refusal is also written to `activity_log`, read later by a different person on a different machine in a different language |
| Store a locale per user | Then a Hindi user's audit entries render in Hindi for the English reader auditing them. The log is a company record, not a personal one |
| Render on the Master using a Master-wide default | Every panel gets the Master's language. That is exactly the outcome a translation layer exists to prevent |

The recipient's locale is known in exactly one place — the browser that is about to paint the
pixels. So that is where rendering happens. The server's job is to say *what happened* in a form
that is language-free and permanent.

### 2.2 Payoff one — the hash chain needs no change

`activity_log` rows are chained by a trigger. The digest input is exact
(`master/src/db/migrations/20260303000000_roles_and_users.ts:268-276`):

```sql
NEW.hash := encode(sha256(convert_to(
    NEW.prev_hash          || '|' ||
    NEW.sequence::text     || '|' ||
    NEW.entity_type        || '|' ||
    NEW.entity_id          || '|' ||
    NEW.action             || '|' ||
    NEW.actor_type         || '|' ||
    COALESCE(NEW.actor_id, '')      || '|' ||
    COALESCE(NEW.details::text, ''), 'UTF8')), 'hex');
```

Eight fields. Every one of them is a permanent fact — an id, an enum-ish token, a JSONB parameter
bag. **None of them is a rendering.** The rendering contract therefore sits entirely outside the
chain: `activityMessageKey('lead', 'stage_changed')` is a function of two values the digest already
covers, evaluated in the browser, and changing the English or the Hindi text changes no byte that
was ever hashed.

This matters because the table refuses to be corrected. `activity_log_immutable()` raises on any
UPDATE and any DELETE (`20260303000000_roles_and_users.ts:305-318`). Had the trail stored English
sentences, translating the product would have required rewriting immutable rows — which is to say it
would have been impossible, and Hindi audit history would have been a permanent gap.

> **Narrowing a claim the original design overstated.** The i18n design said the activity log "needs
> no change at all". That is true of *what the chain covers* and of *what this module writes*. It is
> not true of the table: the Logs module adds `activity_log.actor_name TEXT`
> (`docs/BACKEND_MODULES.md` §5.1), which is safe precisely because it is outside the eight fields
> above. Logs owns that column and the trigger surgery; i18n owns the rendering contract. The two
> designs were answering different questions.

### 2.3 Payoff two — the error envelope needs only additive fields

The HTTP envelope is already `{ error, message, details? }` (`error-handler.ts:28-32`). The socket
ack is already `{ ok: false, error, code?, missingPermission? }`
(`shared/src/protocol/socket.ts:142-159`). Both grow two optional fields, `messageKey` and `params`.
No existing field changes shape, no existing consumer breaks, and `message` stays — it is the third
tier of the client fallback (§5.3) and it is what the Master's own logs print
(`hub.ts:397`).

### 2.4 Payoff three — it does not degrade offline at all

Both catalogues are **compiled into the panel's bundle** by Vite before the panel has ever contacted
a Master. Rendering needs no network, no Master, no cache, no snapshot field. This is the only one
of the six modules that loses nothing when the link drops: language switching works, every screen
renders, and errors already surfaced stay legible because they were never English prose in the
first place. The Office's own invented 503 code, `unavailable`
(`office/src/http/app.ts:444`), renders from `error.unavailable` — in Hindi, while disconnected.

The catalogue is deliberately **not** carried in `SyncSnapshot`. The Office server re-sends the
whole masked snapshot over SSE on every outbox change, so two locales of catalogue would be
re-serialised and re-pushed on every local save; and a panel restarted between full snapshots would
be left holding stale strings. A bundle is the correct home for something that changes only when the
code changes.

## 3. Catalogues are compiled TypeScript, not a database table

**A key exists only because code references it.** That single sentence decides the storage.

| Property | `.ts` catalogue | `catalogue` table |
|---|---|---|
| Misspelt key | Compile error | Renders blank at runtime, on the shop PC, in front of a customer |
| Key referenced but never defined | Compile error | Silent |
| Key defined but never referenced | Findable by grep | Accumulates forever |
| Hindi missing for a new English key | **Build turns red** (§3.1) | Silent mixed-language screen |
| Reaches an offline panel | In the bundle | Needs a sync path, a permission, a conflict story |
| Editable without a developer | No | Yes — see the open question in §14 |

A table would also need a migration, a permission key, a snapshot field and a merge policy, for a
dataset that changes only when someone edits code. That is the whole argument.

### 3.1 `hi.ts` is a TOTAL record, and that is the point

```ts
// shared/src/i18n/hi.ts
export const HI_MESSAGES: Record<MessageKey, string> = { ... };
```

`Record<MessageKey, string>`, **not** `Partial<Record<...>>`. Adding one English key turns the Hindi
build red until Hindi exists. That pressure is exactly right at release time and genuinely
obstructive mid-feature, which is why `tools/i18n-sync.mjs` (§9) exists: it appends the missing keys
with the English text and a `// TODO(i18n-hi)` marker, so the build goes green and the untranslated
strings are one grep away.

The compiler catches a *missing* key. It cannot catch a *wrong* key — a Hindi string that dropped a
`{name}` placeholder still typechecks as a `string`. That is what
`shared/tests/i18n-coverage.test.ts` is for (§12.2).

## 4. `shared/src/i18n/` — the file specification

```
shared/src/i18n/

  hi.ts          Devanagari. Record<MessageKey, string>, total
  keys.ts        MessageKey, Placeholders<S>, ParamsFor<K>, CountKey, LocaleCatalogue
  locales.ts     LOCALES / Locale / isLocale / LOCALE_LABELS / DEFAULT_LOCALE

```

No migration. No table. No permission key (§13).

### 4.1 `en.ts` — one flat object, `as const`

```ts
export const EN_MESSAGES = {
  'permission.lead.convert': 'Convert a lead to an order',
  'module.leads': 'Leads',
  'action.view': 'View',
  'capabilityGroup.workflow': 'Workflow',
  'roleTemplate.sales': 'Sales',

  'error.forbidden.missingPermission': 'You do not have permission: {permission}',
  'error.conflict.nameTaken': 'A {kind} named “{value}” already exists',
  'error.conflict.staleVersion':
    'Somebody else saved this while you had it open (version {storedVersion}).',
  'error.unavailable': 'The Master Panel is unreachable. Try again when the link is back.',
  'error.lockedOut': 'Too many failed attempts. Try again in {seconds} seconds.',

  'activity.lead.stage_changed': '{actor} moved this lead to {to}',
  'activity.user.deactivated': '{actor} deactivated {name}',

  'common.save': 'Save',
  'count.leads.one': '{count} lead',
  'count.leads.other': '{count} leads',
} as const;
```

Rules, each of which a test enforces (§12):

- **Flat, dotted keys.** Not nested objects. A flat object is what makes `keyof typeof` produce a
  usable union, and it is what makes the whole catalogue greppable.
- **`as const` is load-bearing.** Without it every value widens to `string` and `Placeholders<S>`
  has nothing to read. This is not a style choice.
- **Named placeholders, never positional, never concatenation.** `{permission}` survives a
  translator reordering the sentence; `%s` and `'You do not have permission: ' + key` do not.
  Devanagari word order differs from English often enough that this is a practical rule, not a
  purist one.
- **No pre-formatted numbers, no thousands separators, no `₹` inside a message.** Numbers arrive as
  params and are formatted by the caller (§11).
- **Plural forms are two sibling keys**, `.one` and `.other`, never a number glued to a sentence
  (§4.5).

Namespaces:

| Namespace | Holds | Count today |
|---|---|---|
| `permission.*` | One per `CAPABILITIES` entry plus one per module×action key | 12 + 32 |
| `module.*` | One per `MODULES` entry | 7 |
| `action.*` | One per `ACTIONS` entry — the grid's column headers | 6 |
| `capabilityGroup.*` | One per `CAPABILITY_GROUPS` entry | 4 |
| `roleTemplate.*` | One per `ROLE_TEMPLATES` entry | 2 |
| `error.*` | One per `AppError` subclass and per stable code, plus finer per-throw-site tokens | see §7 |
| `validation.*` | Field-level messages | with §7 |
| `activity.*` | `activity.<entityType>.<action>` | see §13 |
| `common.*` | Save, Cancel, Delete, Search, — | small |
| `count.*` | `.one`/`.other` sibling pairs | small |
| `screen.*` | Screen copy — **populated by the UI phase, not this batch** | 0 now |

The 32 module×action keys (`leads.view`, `orders.export`, …) are derived by `moduleKeys()`
(`permissions.ts:117-121`) and have **never had a token**. They are minted here; see §6.4.

**Which namespaces this batch mints, and which the UI phase mints.** The line is not "backend
strings versus screen strings" — it is **whether the token's key set is derivable from something the
backend owns**. A token whose key set comes from a catalogue, an enum or a CHECK constraint is minted
now, because the gate that proves it complete (§12.2) is a pure test over compiled TypeScript and
needs no screen. A token that exists because a designer wrote a sentence on a mockup is minted in the
UI phase, because nothing can prove it complete until the screen exists.

| Minted in **this** batch | Minted in the **UI phase** |
|---|---|
| `permission.*`, `module.*`, `action.*`, `capabilityGroup.*`, `roleTemplate.*` — key sets derived from `PERMISSIONS`, `MODULES`, `ACTIONS`, `CAPABILITY_GROUPS`, `ROLE_TEMPLATES` | `screen.*` — all screen copy |
| `error.*`, `validation.*` — one per `AppError` subclass and per stable code (§7) | `state.*` — the empty/error/offline copy blocks in `07-UI-SPEC.md` §3–§9 |
| `activity.*` — `activity.<entityType>.<action>`, key set pinned by the source-reading gate (§13.3) | `fields.set.*`, `fields.value.*`, `reports.*`, `documents.*`, `dashboard.*`, `bin.restore.*`, `log.chain.*` — screen labels and prose |
| `common.*`, `count.*` — the small shared set the server-side messages need | `month.*` — twelve month names, looked up from the `'YYYY-MM'` label and **never** produced by formatting a `Date` (§11) |

**Reconciling this with `07-UI-SPEC.md` §10.1.** That section lists namespaces *per screen*, which is
the right list for a screen author and the wrong list for this batch's scope. Read against this
table: `module.*` and `permission.*` in 07's list are **already minted here** and the UI phase only
*consumes* them; `log.action.*` and `log.entity.*` are 07's per-screen names for what this document
mints as the single `activity.<entityType>.<action>` namespace (§4.6) — **one namespace, not three**,
and `activityMessageKey()` is the contract both screens render against; `bin.entity.*` is likewise
`activity.*`'s entity half rendered as a noun. Everything else in 07 §10.1 is UI-phase screen copy.
Where the two documents disagree on a namespace's *name*, this document is the i18n authority and
07 is describing screens that do not exist yet.

### 4.2 `keys.ts` — the type machinery

```ts
import type { EN_MESSAGES } from './en.js';

export type MessageKey = keyof typeof EN_MESSAGES;

/** The {named} placeholders inside a literal message template. */
export type Placeholders<S extends string> =
  S extends `${string}{${infer Name}}${infer Rest}` ? Name | Placeholders<Rest> : never;

export type MessageParams = Record<string, string | number>;

type ParamsOf<K extends MessageKey> = Placeholders<(typeof EN_MESSAGES)[K]>;

/**
 * `[]` when a message has no placeholders, so `t('common.save')` compiles with
 * one argument; a required record otherwise, so a missing placeholder, an
 * invented one, and params passed to a message that takes none are all compile
 * errors.
 */
export type ParamsFor<K extends MessageKey> =
  [ParamsOf<K>] extends [never] ? [] : [params: Record<ParamsOf<K>, string | number>];

/** Stems that have BOTH a `.one` and an `.other` sibling — the only valid tCount inputs. */
export type CountKey = {
  [K in MessageKey]: K extends `${infer Stem}.other`
    ? `${Stem}.one` extends MessageKey ? Stem : never
    : never;
}[MessageKey];

export type LocaleCatalogue = Readonly<Record<MessageKey, string>>;
```

`ParamsFor` is the piece that earns its keep. It is a **tuple** type spread into the signature, so:

```ts
t('common.save');                                            // ok
t('common.save', { x: 1 });                                  // compile error: expected 1 argument
t('error.forbidden.missingPermission');                      // compile error: expected 2 arguments
t('error.forbidden.missingPermission', { permission: k });   // ok
t('error.forbidden.missingPermission', { permision: k });    // compile error: unknown property
```

`[ParamsOf<K>] extends [never]` — the tuple wrapper is deliberate. A bare `ParamsOf<K> extends never`
distributes over the union and silently produces `never` for keyed messages.

### 4.3 `locales.ts`

```ts
export const LOCALES = ['en', 'hi'] as const;
export type Locale = (typeof LOCALES)[number];
export const DEFAULT_LOCALE: Locale = 'en';

export function isLocale(value: unknown): value is Locale {
  return typeof value === 'string' && (LOCALES as readonly string[]).includes(value);
}

/**
 * Each language named in its OWN script — deliberately NOT translatable. A
 * picker that renames the language you cannot read into the language you cannot
 * read is useless.
 */
export const LOCALE_LABELS: Record<Locale, string> = {
  en: 'English',
  hi: 'हिन्दी',
};
```

`isLocale` follows the `isRoleTier` / `isPermission` shape already in the codebase
(`permissions.ts:30-32`, `permissions.ts:139-141`) so an unknown value off the wire, out of
`localStorage`, or out of an env var is narrowed the same way everywhere.

### 4.4 `translate.ts` — `t()`

```ts
export interface Translator {
  readonly locale: Locale;
  t<K extends MessageKey>(key: K, ...params: ParamsFor<K>): string;
  tCount<S extends CountKey>(stem: S, count: number, params?: MessageParams): string;
}

export function createTranslator(locale: Locale): Translator;
export function resolveCatalogue(locale: Locale): LocaleCatalogue;
export function t<K extends MessageKey>(locale: Locale, key: K, ...params: ParamsFor<K>): string;
```

Substitution is one regex and nothing else:

```ts
const PLACEHOLDER = /\{(\w+)\}/g;

function fill(template: string, params: MessageParams): string {
  return template.replace(PLACEHOLDER, (whole, name: string) =>
    Object.prototype.hasOwnProperty.call(params, name) ? String(params[name]) : whole,
  );
}
```

Two rules encoded in nine lines:

- **`String(value)` and no `Intl.NumberFormat`.** `t()` has no number-formatting capability *at all*.
  The rule in §11 — that numbers, ids and fingerprints are never localised — is enforced by the
  function being unable to break it rather than by a comment asking nicely.
- **An unknown placeholder is left literally in place**, not blanked. `{taluka}` on screen is a
  visible bug report; an empty gap is a mystery.

**The missing-key fallback, and a correction to the original design.** Because `MessageKey` is a
compile-time union, a key can only be missing at runtime when it arrived as a *string off the wire* —
an `messageKey` from a newer Master than this panel's bundle. The order is:

1. the requested locale's catalogue;
2. `EN_MESSAGES` (a key that exists in English but not yet in Hindi — impossible while the total
   `Record` holds, but cheap insurance if the sync script were ever run with `Partial`);
3. **the raw key, returned verbatim.**

The design proposed "a readable fallback derived from the key". That is rejected. Deriving prose from
a key is precisely what `PermissionGrid.humanise` does (`PermissionGrid.tsx:211-216`), and deleting
that function is one of this module's goals (§6.4). Re-implementing it inside `t()` would resurrect
the second, silently divergent source of English at the centre of the module built to remove it. A
raw key on screen is ugly, honest, greppable and impossible to mistake for a translation. It is
never blank and it never throws — that part of the design stands.

### 4.5 `tCount()`

```ts
tCount('count.leads', n, { … })  →  n === 1 ? 'count.leads.one' : 'count.leads.other'
```

Selection uses `Intl.PluralRules(locale)` — ECMA-402 core, in Node and in every browser this ships
to, no network, no DOM, no dependency. English and Hindi share the same two-category set
(`one`, `other`), so one mechanism covers both target languages exactly.

`count` is injected as the `{count}` param, so the sentence is authored whole in each language and a
number is never concatenated onto it. `{count}` is a number and therefore not reformatted (§11).

### 4.6 `activity.ts` — the contract the Logs module renders against

```ts
export type ActivityToken = `activity.${string}.${string}` & MessageKey;

/** The frozen, APPEND-ONLY set. See §13. */
export const ACTIVITY_TOKENS: ReadonlySet<string>;

/** `activity.<entityType>.<action>` when the catalogue holds it, else null. */
export function activityMessageKey(entityType: string, action: string): MessageKey | null;

export interface ActivityRenderInput {
  entityType: string;
  action: string;
  actorName: string | null;
  details: Record<string, unknown> | null;
}

/** Renders, or falls back to the raw pair — honestly, never blank. */
export function renderActivity(t: Translator, input: ActivityRenderInput): string;
```

`activityMessageKey` returns `null` rather than throwing, and `renderActivity` falls back to showing
the raw `entity_type` / `action` pair. This is not defensive coding for a case that cannot happen:
`action` is free-form `TEXT` with **no `CHECK` constraint**, so a row whose action predates or
post-dates this bundle's catalogue *will* occur (§13). Showing `lead · stage_changed` is a worse
sentence than the translated one and a far better outcome than a blank cell in an audit trail.

**Append-only.** `activity_log` refuses UPDATE and DELETE by trigger
(`20260303000000_roles_and_users.ts:305-318`), so retiring a token would orphan rows that can never
be corrected. The rule is enforced by `shared/tests/activity-tokens.lock.json` (§12.2) — and
honestly, by a person who could edit the lockfile. The comment above `ACTIVITY_TOKENS` states the
real justification, because a lockfile is a speed bump and the reasoning is the actual guard.

### 4.7 `errors.ts` — one wire shape for both transports

```ts
export interface ErrorPayload {
  /** Stable code — branch on this, never on the message. */
  error: string;
  /** English, derived from messageKey. The last-resort render tier. */
  message: string;
  messageKey?: MessageKey;
  params?: MessageParams;
  details?: Record<string, unknown>;
}

export function hasMessageKey(value: unknown): value is { messageKey: MessageKey };

/** The coarse `error.<code>` token for any failure whose thrower named no finer one. */
export function errorMessageKey(code: string): MessageKey;
```

Declaring the payload once is what stops the HTTP envelope and the socket ack drifting apart again —
they have already drifted once, which is why `details` reaches the browser over HTTP
(`error-handler.ts:31`) and dies at the socket (`hub.ts:399-404`).

`errorMessageKey` must be **total over every stable code the two servers emit**, with `error.unknown`
as the last resort. The codes today:

| Origin | Codes |
|---|---|
| `master/src/lib/errors.ts` | `validation_error`, `unauthorized`, `forbidden`, `tenant_violation`, `not_found`, `conflict` |
| `error-handler.ts:9,37` | `not_found` (unknown endpoint), `internal_error` |
| `office/src/http/app.ts` | `unavailable`, `master_command_failed`, `invalid_request`, `not_signed_in`, `not_synced`, `permission_denied`, `queue_failed`, `scan_failed`, `sign_in_failed`, `pairing_failed` |
| `office/src/services/user-session.service.ts` | `invalid_credentials`, `locked_out`, `unknown_here` |

`locked_out` is the instructive one. Its English message today interpolates a computed number
(`user-session.service.ts:91`: `` `Too many failed attempts. Try again in ${…} seconds.` ``). Under
this module it becomes `error.lockedOut` with `{ seconds }` — a token and a param, which is the
whole pattern in one line.

### 4.8 `pseudo.ts` — `en-XA`

```ts
export const PSEUDO_LOCALE = 'en-XA';
export function buildPseudoCatalogue(): LocaleCatalogue;
```

Every English string padded to **1.4×** and bracketed: `Save` → `[Sáávéé —————]`. Placeholders are
left untouched, so a padding bug cannot masquerade as a substitution bug.

This exists to make the design spec's 1.4× expansion budget *checkable*. `docs/UI_REDESIGN.md`
§8 Phase 4 lists a Density gate — *"all three densities render every screen at 1366×768, no
clipping, no horizontal scroll"* — and the same sentence with `en-XA` selected is the string-expansion
gate. Without a pseudo-locale, "survives 1.4× expansion" is an aspiration nobody can fail.

`en-XA` is **not** a `Locale`. It never appears in `LOCALES`, so `isLocale('en-XA')` is false and it
cannot arrive from `localStorage`, an env var or the wire. It is reachable only through the dev flag
in the picker (§5.4). Whether it ships in production builds at all is an open question (§14).

### 4.9 The barrel, and two packaging edits

```ts
// shared/src/index.ts — a twelfth line beside the existing eleven
export * from './i18n/index.js';
```

`shared/package.json` declares exactly one `exports` entry (`"."`), so a new directory is invisible
to the other four workspaces until it is re-exported here. Verified: the barrel is eleven
`export *` lines today.

**`shared/package.json` also gains `"sideEffects": false`.** This module is the **first runtime
import either web bundle takes from `@orderbook/shared`**. All 24 import sites across
`master/web/src` and `office/web/src` are `import type` today — verified by grepping
`from '@orderbook/shared'` (24 hits, 12 per package) and confirming each is a `type` import.

`prestart:*` scripts build it; a bare `npm run build --workspace @orderbook/master-web` does not.
That has been harmless while every import was type-only — a stale `shared/dist` produced a type error
at worst. From this module onward a stale `dist` is **a missing-strings bug at runtime**, on the shop
PC, with no error in the console.

### 5.2 `storage.ts` — the three-step locale fallback

### 5.3 `useErrorMessage.ts` — three tiers, never blank

```ts
export function renderApiError(t: Translator, err: ApiError): string {
  if (err.messageKey) return t(err.messageKey as MessageKey, err.params ?? {});  // 1
  const coarse = errorMessageKey(err.code);
  if (coarse) return t(coarse);                                                  // 2
  return err.message;                                                            // 3
}
```

| Tier | Renders | When |
|---|---|---|
| 1 | The precise token the thrower named, in the reader's language | Normal |
| 2 | `error.<code>` — the coarse token for the stable code | A throw site with no finer token (only possible if §7 lands as *optional*) |
| 3 | `err.message` — the server's English | An unrecognised code from a newer server than this bundle |

**Tier 3 is why `message` stays on the envelope.** Deleting it would make the one case this fallback
exists for render blank. English on a Hindi screen is bad; nothing on a Hindi screen is worse, and a
person cannot even report what they saw.

The Office copy additionally maps `unavailable` → `error.unavailable`, the panel's own invented code
with no Master origin (`office/src/http/app.ts:444`).

### 5.5 `<Untranslated>` — a semantic wrapper, not a disable comment

```tsx
<Untranslated>{order.id}</Untranslated>
```

The lint rule (§8) skips its children. So does `// eslint-disable-next-line`. The difference is what
the reader learns six months later:

| | Says | Survives |
|---|---|---|
| `// eslint-disable-next-line` | "a rule fired here and somebody silenced it" | Nothing — a rule rename or a config change orphans it |
| `<Untranslated>` | "this string is an **identifier**, and identifiers are never translated" (§11) | It is the code. Grep finds every deliberate exception in the product in one search |

The category matters: record ids, device codes, permission keys, chain fingerprints and product codes
must **never** be translated or reformatted. `<Untranslated>` names that category in the markup. A
disable comment names the tool. Suppressing correctly and documenting intent become the same action,
which is the only way a suppression affordance stays honest.

`notTranslated(value)` is the non-JSX sibling for a string headed into an attribute.

### 6.2 `respond()` — the defect this module is obliged to fix

`master/src/realtime/hub.ts:391-406`, verbatim:

```ts
operation()
  .then((data) => ack({ ok: true, data }))
  .catch((error: unknown) => {
    log.warn(`Command failed: ${toErrorMessage(error)}`);

    if (error instanceof ForbiddenError) {
      ack({ ok: false, error: error.message, missingPermission: error.permission });
      return;
    }

    ack({ ok: false, error: toErrorMessage(error) });
  });
```

`code` is **never set**, on either branch. `CommandResult.code` is declared and documented as
load-bearing (`socket.ts:145-155`), and `office/src/http/app.ts:454` branches on
`code === 'forbidden' ? 403 : 502` — a condition that is **permanently false**. Every Office-panel
refusal, permission denials included, reaches the Office browser as `502 master_command_failed`.

This module must not ship a token into a client that has already mislabelled the failure, so
`respond()` is rewritten to set `code`, `details`, `messageKey` and `params` for any `AppError`:

```ts
if (error instanceof AppError) {
  ack({
    ok: false,
    error: error.message,
    code: error.code,
    messageKey: error.messageKey,
    params: error.params,
    ...(error.details ? { details: error.details } : {}),
    ...(error instanceof ForbiddenError ? { missingPermission: error.permission } : {}),
  });
  return;
}
```

`missingPermission` is kept beside `details.permission` rather than replaced: `MasterCommandError`
reads it at `master-connection.ts:257` and `forward()` spends it at `app.ts:457-459`. Removing it is
a separate change with no benefit here.

The full path a token travels, end to end:

```
service throw  →  hub respond()  →  socket ack (CommandResult)
               →  MasterCommandError  →  forward()  →  Office browser  →  t()
```

Four hops, each of which currently drops something. A test asserts the whole path (§12.3).

## 7. THE OPEN QUESTION — is `messageKey` required on `AppError`?

This is the single largest scoping decision in the whole batch, it must be answered **before any
throw site in any of the five other modules is written**, and it is the owner's call.

### 7.1 The two options

```ts
// REQUIRED
class AppError extends Error {
  constructor(
    readonly messageKey: MessageKey,
    readonly params: MessageParams,
    readonly statusCode: number,
    readonly code: string,
    readonly details?: Record<string, unknown>,

class AppError extends Error {
  constructor(
    message: string,
    readonly statusCode: number,
    readonly code: string,
    readonly details?: Record<string, unknown>,

    readonly params?: MessageParams,

}
```

### 7.3 Why `message` must stay byte-identical

Under **required**, `message` is no longer authored — it is `t('en', messageKey, params)` evaluated
at throw time. That is deliberate: one token means the English fallback can never drift from the
Hindi rendering.

It also means **every existing test asserting on English message text must keep passing unchanged**.
`master/tests/access.integration.test.ts` and `master/tests/permissions.integration.test.ts` both
assert on `.message`. The EN catalogue entry for each converted throw site must therefore reproduce
the current English **byte for byte**, including the typographic quotes and the em dashes already in
those strings. This is not a place to improve the wording. Any rewording is a separate, deliberate
commit — otherwise a legitimate translation change looks identical to a broken test.

`ForbiddenError` is the model: `` `Missing permission: ${permission}` `` (`errors.ts:51`) becomes
`'error.forbidden.missingPermission': 'Missing permission: {permission}'`, with `{ permission }` as
params. Same bytes, now a token.

### 7.4 Recommendation

**Required.** The work is wide but genuinely mechanical — 129 call sites resolving to **68** tokens,
one EN string and one HI string each, no logic — and it is the only option that makes an untranslated
error *impossible*. Optional is
two lines of work now and an open hole forever, guarded by nothing: a developer who writes
`new ValidationError('some prose')` next month gets a message that renders in English on a Hindi
screen, and **no test can catch it**, because `message` still populates and the envelope still
validates.

Given the owner overruled deferring this module at all, "translated eventually, by convention" is not
the intent.

**This is the owner's decision, not the implementer's.** It changes the size of every one of the five
sibling modules.

## 8. The lint gate

`tools/eslint-rules/no-untranslated-jsx-text.js`, plus `tools/eslint-rules/index.js` exporting a
local plugin object, registered in `eslint.config.js`. **In-repo, flat-config, no new dependency** —
the repo runs ESLint 9 with `typescript-eslint` and nothing else (`package.json` devDependencies),
and adding `eslint-plugin-i18next` for one rule would be a network-installed dependency in a project
whose defining constraint is that it never touches the network.

What it flags:

- `JSXText` nodes containing at least one letter;
- string literals passed to `placeholder`, `title`, `aria-label`, `alt`, `label`.

What it skips: children of `<Untranslated>`; punctuation-only and digit-only text; `*.test.tsx`.

Scope: `files: ['{master,office}/web/src/**/*.tsx']`. Scoping to the web trees is what keeps the
false-positive rate survivable — server files are full of legitimate literals (log messages, SQL,
column names, migration text) that no person ever reads.

### 8.1 The honest false-positive story

**Expect 10–20% false positives on the first run** over the existing ~4,000 lines of JSX, in three
clusters:

| Cluster | Example | Correct fix |
|---|---|---|
| Unit symbols and separators | `kg`, `%`, `×`, `·`, `—` | `<Untranslated>` |
| Identifiers on screen | `<code>{permission}</code>`, record ids, device codes, chain hashes | `<Untranslated>` — and this cluster is the *reason* the affordance is a component (§5.5) |
| Punctuation glue between elements | `(`, `)`, `:` | `<Untranslated>`, or restructure |

The third cluster is the annoying one and the second is the important one: those strings must
**never** be translated, so the rule firing on them is not a false positive at all — it is the rule
asking a question that has a real answer, and `<Untranslated>` is that answer written down.

The rule's message names `<Untranslated>` as the preferred fix rather than offering a blanket
disable.

**This batch registers the rule as `'off'` and does not sweep the existing JSX.** That is the
ruling, and it supersedes this section's earlier recommendation of `'warn'`. The sweep is the UI
phase's work (`docs/UI_REDESIGN.md` §8), and the rule is promoted to `'warn'` or `'error'` when that
sweep lands.

The reason is `verify`'s shape, not the rule's merits. **`lint` is the first step of
`npm run verify`** — `lint && typecheck && test` — so it runs before a single test does. Against
~4,000 unswept lines of JSX the rule would emit hundreds of findings on day one, at the top of the
one command every stage gate in `11-BUILD-SEQUENCE.md` §5.1 depends on. Even at `'warn'` that is
hundreds of lines of scrollback standing between the implementer and the test summary they are
required to read two numbers off (`10-TESTING.md` §5). The gate that exists to catch a silently
skipped suite must not be buried under warnings about a sweep nobody has been asked to do yet.

Registered-but-`'off'` keeps what is actually valuable now: the rule is **in the repo, in the flat
config, and one word away from firing**. The UI phase turns it on and immediately has a real count,
rather than starting by writing a rule. `05-EXISTING-CODE-CHANGES.md` is the authority on the
`eslint.config.js` edit.

The alternative that was rejected — landing it as `'error'` scoped to a hand-maintained list of
already-converted files — needs exactly the kind of list `HANDOFF.md:512-515` warns against, and it
goes stale the first time somebody converts a file and forgets the list.

## 9. `tools/i18n-sync.mjs`

```
npm run i18n:sync
```

Reads `EN_MESSAGES`, computes `MessageKey \ keyof HI_MESSAGES`, and appends each missing key to
`hi.ts` with the English text and a `// TODO(i18n-hi)` marker. Idempotent. Never edits an existing
Hindi string and never deletes one — deletion is a human decision, because a key removed from
English may be about to come back under a different name.

It is what makes §3.1's total `Record` workable instead of obstructive: add an English key, run the
script, keep working, and `grep -c 'TODO(i18n-hi)' shared/src/i18n/hi.ts` is the release checklist
item.

`.mjs` and plain Node — no build step, no dependency, consistent with the repo having no other
codegen.

## 10. Devanagari

Two separate problems with two separate owners. Do not conflate them.

| Surface | Owner | Requirement |
|---|---|---|
| The browser UI | **UI phase** — both the stack and the faces (`docs/UI_REDESIGN.md` §1). `styles.css` is a web file and is deferred (§5.6); §10.1 below is the specification the UI phase implements, not work in this batch | Devanagari renders in the panels |
| Generated PDFs | PDF Designer (`docs/BACKEND_MODULES.md` §5.5) | Server-side PDFKit + fontkit, vendored SIL OFL `NotoSansDevanagari-Regular`, a **hard requirement** with a pure test gate |

### 10.1 The font stack

`master/web/src/styles.css:26` and `office/web/src/styles.css:26` are identical today:

```css
font-family: 'Segoe UI', Tahoma, Arial, sans-serif;
```

None of those three faces covers Devanagari. Hindi renders as tofu boxes, and **there is no CDN to
fall back to** — `docs/UI_REDESIGN.md` §1 records that both `vite.config.ts` files already forbid
reaching one. The interim stack:

```css
font-family: system-ui, 'Segoe UI', 'Nirmala UI', Tahoma, Arial, sans-serif;
```

`Nirmala UI` ships with Windows and is the offline-safe fallback on the target hardware. The
monospace stack (`styles.css:201`) is left alone: it renders ids and codes, which are never Devanagari
(§11).

**This is an interim measure and it is honest about being one.** `docs/UI_REDESIGN.md` §1 already
commits to self-hosting Inter, IBM Plex Mono and **Noto Sans Devanagari** as local `.woff2` files with
local `@font-face`, gated by a cold-run-makes-zero-requests check. When that lands, the `.woff2`
faces lead the stack and `Nirmala UI` becomes the fallback behind them. Bundling a Devanagari face as
a base64 data URI in `styles.css` (~200–400 KB per bundle) is the alternative if the UI phase slips —
flagged in §14, because a stripped Windows install or a future Linux deployment has no `Nirmala UI`
and would show boxes with no diagnosis.

### 10.2 Line height and layout

Devanagari needs vertical room that a Latin-tuned stylesheet does not give it. Matras sit above the
headline and conjuncts descend below it, so a `line-height` that looks generous in English clips in
Hindi.

- **Minimum `line-height: 1.5`** on body text and on anything that can hold a translated string;
  1.2–1.3 is normal for Latin UI and visibly clips Devanagari.
- **No fixed-height text containers.** Badges, status pills, Kanban stage chips and table headers
  must size to content.
- **No `text-transform: uppercase`** on a translatable string — Devanagari has no case, so the rule
  is a no-op in Hindi and the two languages stop matching visually.
- The 1.4× budget (§4.8) hits the same components hardest: the permission grid's column headers and
  the Kanban stage chips are the tightest surfaces in the product today.

These are constraints on the UI phase, recorded here because this module is what makes them matter.

## 11. Numbers, ids and fingerprints are NEVER translated or reformatted

The rule, stated once:

> A number is a number in both languages. An identifier is not language at all.

| Category | Example | Rule |
|---|---|---|
| Money | `₹1,23,456.00` | `en-IN` grouping (lakh/crore), Western Arabic digits, **always** |
| Counts and quantities | `12 boxes` | `{count}` param, digits unchanged |
| Record ids | `RL0000000004` | Verbatim, `<Untranslated>` |
| Device codes, pairing codes | — | Verbatim |
| Chain hashes | 64 hex chars | Verbatim, monospace |
| Permission keys | `field.saleRate.view` | Verbatim in a `<code>` — the *label* is translated, the key is not |
| Product codes, party codes | — | Verbatim |
| Dates and times | — | Formatted, but never with Devanagari digits |

Devanagari digits (`१२३`) are the specific failure this prevents. They are correct Hindi orthography
and completely wrong here: a record id in Devanagari digits cannot be typed into a search box, read
out over a phone, or matched against a printed document. Money in Devanagari digits is unreadable to
the accountant and to the customer.

Enforcement, in four layers:

1. **`t()` has no formatting capability.** `String(value)` and nothing else (§4.4). It cannot break
   the rule.
2. **The EN catalogue contains no pre-formatted number, no thousands separator and no `₹`.** A test
   asserts it (§12.1).
3. **`format.ts` is pinned explicitly, in both packages — in the UI phase** (`format.ts` is a web
   file, §5.6; the rule is stated here because this is where the reasoning lives). Today
   `formatMoney` already passes
   `'en-IN'` (`master/web/src/format.ts:6`) — but `formatDateTime` calls
   `new Date(iso).toLocaleString()` **with no locale argument** (`format.ts:23`), which means it
   already follows whatever the browser reports. Both get an explicit locale and a header comment
   saying why, so a later "improvement" that threads the UI locale through is a change someone has to
   argue for rather than one that happens by omission. The Office copy is byte-identical today
   (`diff master/web/src/format.ts office/web/src/format.ts` is empty) and must stay so.
4. **`<Untranslated>`** documents the identifier category at the point of use (§5.5).

**Date safety carries over unchanged.** `HANDOFF.md` records that `DATE` columns came back a day
early east of UTC because `toISOString()` converts to UTC first; `toIsoDate`
(`master/src/repositories/mappers.ts:79-90`) is the existing fix. Nothing in this module constructs
a `Date` from a `DATE`-derived value, and no formatter added here may.

## 12. Tests and gates

> **`10-TESTING.md` §8 is the sole test register** — file names, kinds and projected case counts live
> there and nowhere else, and `02-FILE-STRUCTURE.md` is the manifest. What follows is *what these
> suites must prove*, not a second list of what files exist. Where a name here and a name there
> disagree, `10-TESTING.md` wins.

Every suite below is **pure** — no `describe.skipIf`, no database. That is not a nicety: it is the
whole reason the web deferral in §5 costs this batch no coverage. The i18n layer is verified end to
end through `shared/tests/` on a machine that has never seen PostgreSQL and never opens a browser.
`HANDOFF.md:529-532` records that a skipped suite reads as a passing one and that the Windows
Postgres lookup was broken for months with every integration gate silently doing nothing. A
translation gate that can skip is not a gate.

### 12.1 `shared/tests/i18n.test.ts` — the renderer

| Asserts |
|---|
| `t()` substitutes named placeholders in both locales |
| A record id, a device code and a 64-char chain hash pass through **byte-identical** |
| An unknown placeholder is left literally in place, not blanked |
| `tCount()` selects `one`/`other` correctly for `en` and `hi`, and never concatenates a number onto a sentence |
| A `MessageKey` absent from a catalogue at runtime returns the raw key — never blank, never a throw |
| **No EN string contains a digit group separator, a pre-formatted number, or `₹`** |

### 12.2 `shared/tests/i18n-coverage.test.ts` — the contract

This is the suite that makes the existing `labelToken` contract **load-bearing rather than
decorative**.

| Asserts |
|---|
| Every key in `PERMISSIONS` has a `permission.<key>` token |
| Every `MODULES` entry has `module.<x>`; every `ACTIONS` entry has `action.<x>` |
| Every `CAPABILITY_GROUPS` entry has `capabilityGroup.<x>` |
| Every `ROLE_TEMPLATES` `nameToken` exists in the catalogue |
| **`HI_MESSAGES` covers every EN key with an IDENTICAL placeholder set per key** |
| `ACTIVITY_TOKENS` is a superset of `shared/tests/activity-tokens.lock.json` |

The placeholder-set assertion is the one the compiler cannot do: a Hindi string that dropped `{name}`
is still a `string`, still satisfies `Record<MessageKey, string>`, and renders a sentence with a hole
in it. Comparing `Placeholders` sets between the two catalogues at runtime is the only way to catch
it.

`activity-tokens.lock.json` is read with `readFileSync` from the test and **never imported** —
`tsc` does not copy JSON into `dist`, so an import would resolve in the IDE and fail in the built
output.

### 12.3 The type-level tests

`tsconfig.test.json` includes `shared/tests/**/*.ts` and `npm run typecheck` runs
`tsc -p tsconfig.test.json`. So type assertions belong in a normal test file and need **no new
fixture project** — a correction to the module design, which proposed one.

Negative assertions use `@ts-expect-error`, which `tsc` verifies in both directions: it errors if the
line below it *compiles cleanly*. That is exactly the property wanted.

```ts
t('en', 'common.save');
// @ts-expect-error — this key requires params
t('en', 'error.forbidden.missingPermission');
// @ts-expect-error — 'permision' is not a placeholder in this message
t('en', 'error.forbidden.missingPermission', { permision: 'x' });
```

Note the runner boundary: `vitest.config.ts` includes only
`{shared,master,office}/tests/**/*.test.ts` — **`.ts`, not `.tsx`**. A test for `<Untranslated>` or
`LocaleProvider` would need a `.tsx` include and a DOM environment, neither of which exists today.
Component tests are therefore **out of scope for this batch**; the rule and the components are covered
by the lint-rule test and by the end-to-end error-path test instead.

### 12.4 `master/tests/i18n-tokens.test.ts` — the source-reading invariant

Written in the established `master/tests/credential-invariants.test.ts` style: `readFileSync` over
`master/src`, in the spirit of *"These tests read the source, which is unusual and is the point"*
(`credential-invariants.test.ts:13`). See §13.3 for what it must and must not match.

### 12.5 The end-to-end error path

## 13. The activity token catalogue gap

`activity_log.action` is **free-form `TEXT` with no `CHECK` constraint** — `ActivityEntry.action` is
typed `string` (`activity-log.repository.ts:38`) and nothing narrows it on the way to the insert
(`activity-log.repository.ts:59`). So `ACTIVITY_TOKENS` cannot be derived. Somebody must own keeping
it complete, and this section names what "complete" means today.

### 13.1 The thirteen real action values

Enumerated by reading every `recordActivity` / `recordDetachedActivity` call site in `master/src`
(24 sites: 10 `recordActivity` — auth 1, role 4, user 5; 14 `recordDetachedActivity` — catalog 4,
lead 3, inventory 2, order 2, panel 2, auth 1):

| Action | Where |
|---|---|
| `created` | 14 sites across role/user/lead/order/party/product/panel/stock |
| `updated` | 29 sites |
| `deleted` | `role.service.ts:237`, `user.service.ts:278`, and two more |
| `restored` | `role.service.ts:278`, `user.service.ts:314` |
| `deactivated` | `user.service.ts:237` — **behind a ternary** |
| `password_reset` | `user.service.ts:356` |
| `password_changed` | `auth.service.ts:250` |
| `sign_in` | `auth.service.ts:367` — **behind a ternary** |
| `sign_in_failed` | `auth.service.ts:367` — **behind the same ternary** |
| `stage_changed` | `lead.service.ts:280` |
| `dispatched` | `order.service.ts:376` |
| `inbound` | `inventory.service.ts:87` |
| `adjusted` | `inventory.service.ts:145` |

Eight entity types today: `user`, `role`, `lead`, `order`, `party`, `product`, `stock`,
`office_panel`.

The catalogue is keyed by the **pair**, not by the action alone — `activity.lead.deleted` and
`activity.role.deleted` are different sentences — so the surface is a subset of 8 × 13, populated for
the pairs that actually occur.

### 13.2 What the sibling modules will add

Each of the five other modules mints audited actions of its own, and each owns adding its tokens in
the same commit as the action:

| Module | Likely new actions |
|---|---|
| Recycle Bin | `deleted` / `restored` for `lead`, `order`, `party`, `product` — new **pairs**, existing verbs |
| Fields | option-list value added / removed, stage reordered, default changed |
| Logs | chain verification run |
| PDF Designer | template created / edited / deleted, `document_export` rendered |
| Reports | export |

**The `'restored'` `ChangeAction`** the Recycle Bin adds to `shared/src/protocol/socket.ts:177`
(today `'created' | 'updated' | 'deleted'`) is a *different* enum from the activity action — one
travels to panels over the socket, the other is written to the audit table. Do not merge them.

### 13.3 The test that keeps the list honest — and the two traps in writing it

`master/tests/i18n-tokens.test.ts` scans `master/src/services/*.ts` and `master/src/domain/*.ts`,
extracts every literal `(entityType, action)` pair, and asserts each has a catalogue token. Two things
will make a naive implementation quietly useless:

1. **Three of the thirteen actions are behind ternaries.** `auth.service.ts:367` is
   `action: success ? 'sign_in' : 'sign_in_failed'` and `user.service.ts:237` is
   `action: input.isActive === false ? 'deactivated' : 'updated'`. A regex for `action: '…'` matches
   **neither branch of either**, and misses three actions out of thirteen. The extractor must collect
   *every* string literal on the `action:` property's expression, not the first one.
2. **`action:` also appears on `publishChange`.** `role.service.ts:247` is
   `publishChange({ entity: 'role', action: 'deleted', id, payload: role })` — a `ChangeAction`, not
   an activity action. Attributing literals to their enclosing `recordActivity(` /
   `recordDetachedActivity(` call is what separates them; scraping `action:` globally conflates two
   enums and produces a test that passes for the wrong reason.

And a third, from §7.2: **read files with `readFileSync`, never by shelling out to `grep`.**
`master/src/domain/conversion.ts` contains a literal NUL byte and `grep` reports it as binary,
skipping its contents entirely. `credential-invariants.test.ts` already uses `readFileSync`
(`credential-invariants.test.ts:16, 22-25`), so following that file's shape avoids the trap for free.

### 13.4 Ownership

> **The `ACTIVITY_TOKENS` list has no automatic source and therefore needs a person.** This module
> populates the thirteen actions and eight entity types that exist today. Every module that mints a
> new audited action adds its token in the **same commit**, and
> `master/tests/i18n-tokens.test.ts` turns red if it does not. That test is the mechanism; the
> ownership is the decision.

**And the signature changes here, in Stage 1.** `recordActivity` becomes
`recordActivity(entry, actor, trx)` as part of this module, **not** at the Logs stage where
`activity_log.actor_name` is added. The `actor` parameter is harmless before the column exists — it
is accepted and simply not persisted — and introducing it now means Recycle Bin (Stage 2) and Fields
(Stage 3) are written **once** against the final signature instead of being swept when Logs lands.
`20260307` adds the column and starts persisting it; nothing about the call sites changes at that
point. The source-reading gate in §12.4 reads the same call sites either way, so it costs the gate
nothing. `recordDetachedActivity` is untouched and remains forbidden in new modules.

## 14. Open questions

Marked as questions rather than answered, because each is a genuine judgement call.

1. **Is `messageKey` required on `AppError`?** §7. 129 throw sites. **Recommended: required.** This
   must be answered before any sibling module is built.
2. **Should this module be permission-gated?** The locked decision is that all six modules are
   permission-gated and reachable from both panels. This one has **no server surface to gate** —
   `docs/BACKEND_MODULES.md` §7 mints no i18n key, and the picker writes only `localStorage`, is
   per-browser-profile, and changes nothing any other person sees. Gating it behind `settings.manage`
   (tier `admin`) would stop an office-tier user reading their own screen in Hindi, which inverts the
   module's purpose. **Recommended: ungated, as a ratified exception.** If overruled, the key is
   `settings.language`, a new `CAPABILITIES` entry in group `admin`, deliberately **left out of**
   `MINIMUM_TIER` so it defaults to tier `office` and every tier may hold it — adding it to
   `MINIMUM_TIER` reintroduces the exact problem.
3. **Should a Devanagari face be embedded as a base64 data URI (~200–400 KB per bundle), or is
   depending on Windows' `Nirmala UI` acceptable until the UI phase self-hosts `.woff2`?** §10.1.
   A deployment-environment question the code cannot answer. **Promoted** to `README.md` §8 and
   `11-BUILD-SEQUENCE.md` §2.1, with the detail staying here — it was raised in this document and
   visible nowhere else, which is how a question becomes an omission. Note it concerns only the
   **web** face; the server-side PDF face is vendored under `master/assets/fonts/` and is not in
   question.
4. **Should Hindi ship complete or partial?** A total `Record` turns the build red until every key is
   translated; `Partial` plus runtime English fallback ships sooner and shows mixed-language screens.
   **Chosen: total** (§3.1). The trade-off is real and the owner may reverse it.
5. **Is any COMPANY data expected to be translatable** — pipeline stage names, option list labels,
   role names, product names? **Assumed not**: these are already tenant-editable rows, and a company
   that renames a stage to "Quoted" means that word in both languages. If bilingual stage names are
   wanted, that is a **schema** change (a `label_hi` column, or a `labels` JSONB per row) and it
   belongs to the Fields module, not here.
6. **Does the owner want an in-app string editor later?** §3's argument against a table assumes
   strings are edited only by whoever edits the code. If a non-developer must reword a message on the
   shop PC, the decision changes and the module needs a table, a permission key
   (`settings.manage` is the right gate and already enforces nothing) and a snapshot story.
7. **Should `en-XA` ship in production builds behind a hidden flag, or be stripped?** Shipping it
   makes layout regressions checkable on the actual machine; stripping keeps the bundle honest.
8. ~~**Does the lint rule land as `warn` or as `error`-on-converted-files?**~~ **DECIDED: neither —
   it lands registered and `'off'`, and is promoted in the UI phase.** §8.1. `lint` is the first step
   of `verify` and there are ~4,000 unswept lines behind it.

## 17. Known-open, and deliberately not closed here

Context, not work. Each is recorded in `docs/BACKEND_MODULES.md` §8 and none is a side effect of this
module:

- `applied_mutations` atomicity — pre-existing, untouched.
- `panel:revoked` is declared and never emitted — pre-existing, untouched.
- The audit trail's 14 `recordDetachedActivity` call sites across six existing services. **New
  modules must use `recordActivity(entry, actor, trx)`** — the three-argument form, which lands in
  **Stage 1** with this module and not at the Logs stage (§13.4). `recordDetachedActivity` remains
  forbidden in new modules; converting the existing fourteen is separate work.
- The Office snapshot's lack of **module-level** filtering. `forCurrentUser()`
  (`office/src/http/app.ts:395-407`) re-masks `field.saleRate.view` for whoever is signed in now —
  that half is fixed and correct — but it does not filter collections by `*.view`. This module adds
  no snapshot field, so it does not widen the hole.
- Retention and pruning for `activity_log` and `document_exports`.
- Large CSV/PDF payloads over the 15-second socket ack (`master-connection.ts:242`). This module
  sends only tokens and small param bags, so it adds nothing to that payload.
- `master/src/domain/conversion.ts:81` builds a composite stock key inline with a literal NUL byte
  instead of `stockKey()` (§7.2). Nothing is broken today; it needs its own owner.
