## Corrected design

## E — Product and party attributes, and the whole-record-replace data-loss bug

**Verdict.** Two defects share one root: nothing in the repo owns the statement "which wire field is which column", so five hand-maintained copies have drifted, and the two living in the repositories (`columnsFrom`) enumerate every column unconditionally, turning an update into a full replace. The fix is one canonical map in `shared`, a `columnPatch()` that writes only asserted keys, a `stampFieldHlc()` that stops every online write emptying the per-field clock the offline merge depends on, and — the part the first draft missed — a **validation function the merge path can call**, because `mergeUpdate` writes columns with no service in front of it.

The load-bearing decision: a **true partial patch**, not a full-object contract, because the offline path is already partial (`fields: Object.keys(payload)`, office/src/http/app.ts:849) and disagreeing with it would give one record two meanings of "edit". Contract: **`undefined` = not asserted, `null` = clear it.**

### 1. What is actually true

`columnsFrom()` (product.repository.ts:323-346, party.repository.ts:252-267) emits all 20 / all 12 columns with `?? null` and is spread straight into `.update()`. Any caller omitting a key nulls that column.

**Reachability, verified, because it changes the recovery answer.** master/web/src/api.ts has `createParty` (:404) and `createProduct` (:411) and no `put<`/`patch<` at all — master has no product or party screen (`ls master/web/src/screens/` confirms). The Office drawers `queue()` into the outbox (office/src/http/app.ts:245, :258), arriving as `product.update`/`party.update` and routed to `mergeUpdate()` (sync.service.ts:281-283), which never touches `columnsFrom`. `PUT /api/products/:id` (data.routes.ts:265-272) and the `product:update` socket command (hub.ts:343) do call it; a repo-wide grep finds no caller of either. So: **a loaded gun, not a smoking one.** It fires the first time workstream D ships a master form, or requirement 13's REST client sends a partial body. Design it as data loss — it is — but do not tell the owner his catalogue is already destroyed.

**The bug that is firing** is `fieldHlc: {}` at catalog.service.ts:73, :106, :300, :344 (also conflict.service.ts:120, auth.service.ts:104, :242). `mergeFields` (merge.ts:81) treats `storedHlc === baseHlc` as an ordinary sequential edit; with the stored map emptied both are `undefined`, so **every offline edit is accepted unconditionally with no conflict recorded**, including one overwriting a strictly newer Master value. merge.ts:88-116 is dead code today. lead.service.ts:220-222 does it correctly.

Third: COLUMN_MAP's product entry maps `notes: 'notes'` (sync.service.ts:123) and `products` has no `notes` column; `field in columns` passes at :374 and `patch.notes` hits a nonexistent column. Fourth: order.service.ts:250-251 writes `fieldHlc[column] = hlc` with the **snake_case** name while `mergeFields` keys by wire field — order clocks are written under keys the merge never reads. lead.service.ts:221 gets this right via `columnToField()`.

### 2. The fix, at the root

**2.1 `shared/src/domain/columns.ts` (new).** `PRODUCT_COLUMNS`, `PARTY_COLUMNS`, `LEAD_COLUMNS`, `ORDER_COLUMNS`, `USER_COLUMNS` as `const satisfies Record<string,string>`; `JSON_COLUMNS = new Set(['custom_fields','parameters'])`; `assertedFields(input, columns)`; `columnPatch<M extends Record<string,string>>(input: Partial<Record<keyof M, unknown>>, columns: M)` — generically typed so passing the wrong map is an error; `fieldFor(columns, column)` (a linear reverse lookup; it runs once per restored conflict field, no index needed).

Net deletion: sync.service.ts:81-131 COLUMN_MAP + JSON_COLUMNS, lead.service.ts:455-468, user.service.ts:406-416, and the two `columnsFrom` bodies collapse into it. `MERGEABLE_COLUMNS = { lead, order, party, product: MERGEABLE_PRODUCT_COLUMNS }`; `MergeableEntity = keyof typeof MERGEABLE_COLUMNS`. `USER_COLUMNS` is deliberately **not** in it — users have no merge path; it exists only to delete the duplicate.

The `notes` bug disappears by construction: no `notes` key, because no such column.

**2.2 `MERGEABLE_PRODUCT_COLUMNS = PRODUCT_COLUMNS minus categoryId`.** The merge cannot run `resolveCategoryId` (product.repository.ts:353-372), and `products_category_fk` (20260302000000:551) turns a stale id into a hard error. Category assignment stays online-only.

**2.3 `validateProductInput(input)` — a pure function beside the columns map.** Checks only asserted keys: `uom ∈ {box,sqft,piece}`, `peiRating` 0-5, `edgeType ∈ {rectified,non_rectified}`, `application ∈ {floor,wall,floor_wall,outdoor}`, `gstRatePct` and `waterAbsorptionPct` 0-100, `mrp`/`purchaseRate` ≥ 0. Throws the existing `ValidationError` with MessageKeys (`validation.product.uom.unknown`, `.peiRating.range`, `.edgeType.unknown`, `.application.unknown`, `.gstRate.range`, `.waterAbsorption.range`, `.mrp.negative`, `.purchaseRate.negative`). **Called from both `catalog.service` and `mergeUpdate`.** This is not optional: `mergeUpdate` writes columns directly, `applyOne` (sync.service.ts:212-219) catches any throw and records the mutation as permanently `rejected`, and the replay path (:148-151) returns that rejection forever — so a raw CHECK violation silently destroys an Office panel's offline work. A `ValidationError` at least reaches `sync.recentRejections()` with a readable reason.

**2.4 Repositories.**
```ts
function columnsFrom(input: ProductInput, categoryId: string | null) {
  const patch = columnPatch(input, PRODUCT_COLUMNS);
  if (input.categoryId !== undefined || input.categoryName !== undefined) patch.category_id = categoryId;
  else delete patch.category_id;
  return patch;
}
```
No empty-patch guard: `.update()` always also spreads `hlc`, `field_hlc`, `version: trx.raw('version + 1')` and `updated_at`, so the object is never empty. `insertProduct` becomes a partial insert, which is safe because `parameters` is `JSONB NOT NULL DEFAULT '{}'` (20260101000000:110) and `custom_fields` likewise (20260302000000:85) — the constraint every new column must also meet.

Behaviour change to record, not to "fix" back: today a rate-blind editor's update **NULLs** the rate, because `withPermittedRate` deletes the key (visibility.ts:73-76) and `columnsFrom` then writes `?? null`. Under `columnPatch` it is preserved — what visibility.ts:60-68 always claimed.

**2.5 `stampFieldHlc(current, fields, hlc)` in `shared/src/sync/merge.ts`**, beside `mergeFields` as the write-side half of the same invariant. Applied at:
- `createProduct`/`createParty` — `stampFieldHlc({}, assertedFields(input, …), hlc)`.
- `updateProduct`/`updateParty` — load `existing` **inside** the transaction (`findProductById(tenantId, id, trx)`, product.repository.ts:78-89) and throw `NotFoundError` there. catalog.service.ts:320-347 does **not** load the row today; it only calls `findProductByCode` for the clash check. Do not copy `deleteProduct`'s outside-the-transaction read (:376) — two concurrent edits would each read the pre-edit map and the second would drop the first's stamps.
- `conflict.service.ts:110-133 writeRestore` — stamp only `fieldFor(columns, column)` onto the record's current map; restoring one losing value must not wipe the other thirty clocks (this affects leads and orders too, not just products).
- `order.service.ts:251` — `fieldHlc[fieldFor(ORDER_COLUMNS, column)] = hlc`. All five patch keys are in ORDER_COLUMNS.
- `auth.service.ts:104, :242` — stamp `passwordHash` onto the existing map.
- `lead.service.ts:436 initialFieldHlc` stays (it deliberately stamps defaulted `partyId`/`stageId`/`items`); add a comment pointing at `stampFieldHlc`.

**2.6 The client half.** office/web/src/api.ts:314 and :317 widen to `input: PartyInput & { baseFieldHlc?: Record<string,string> }` / `ProductInput & {…}` — spreading an extra key into a parameter typed `ProductInput` is an excess-property error. ProductDrawer.tsx:140 and PartyDrawer.tsx:120 send `baseFieldHlc: editing.sync.fieldHlc`. office/src/http/app.ts:841 destructures it out of the payload before `Object.keys` builds `fields` (the routes at :249/:262 already read it separately).

**2.7 Rate permission on the merge path.** `mergeUpdate` bypasses `withPermittedRate`; `rate` is already mergeable today (sync.service.ts:120), and widening adds `mrp` and `purchaseRate`. Before `mergeFields`, drop (never reject — the same reasoning visibility.ts:60-68 gives) `rate`/`pricePerSqft`/`mrp` without `field.saleRate.edit`, and `purchaseRate` without `field.purchaseRate.edit`. The rule to state once: **MRP is readable by everyone and never masked; it is writable only under pricing, because it is a price on the product record.**

**2.8 Office local view.** local-store.ts:96 `applyOverlay` has no `party.update`/`product.update` case. Generalise `pickLeadFields` (:319) to `pickFields<T>` and add both, mirroring `lead.update` at :101.

### 3. Are damaged rows recoverable?

Detectable only as suspicion — a wiped row and one only ever created through the 8-field drawer are identical (`version > 1 AND finish IS NULL AND … AND parameters = '{}'::jsonb`). **Not recoverable from the activity log:** catalog.service records `action: 'updated'` with no `details` (:307-315, :351-358); the hash chain proves *that* a row changed, never what it held. Recoverable only from a backup (backup-export.service.ts:51 dumps every user table via `listUserTables()`, so new columns ride along automatically) or an Office panel's on-disk snapshot (`paths().snapshotFile`). Without one of those two, **the values are gone.**

### 4. New attributes

Rule: **columns** for anything indexed, constrained, arithmetic or standard-defined; **option lists** for vocabularies staff extend; **custom fields** for none of these. Money follows `rate` — INTEGER paise. Percentages and measurements follow `thickness_mm` — NUMERIC.

`products`: `mrp INTEGER`, `purchase_rate INTEGER`, `gst_rate_pct NUMERIC(5,2)`, `uom TEXT NOT NULL DEFAULT 'box'` (CHECK box/sqft/piece), `barcode TEXT` (partial-unique), `brand TEXT` (list `product.brand`), `shade TEXT` (list `product.shade`), `calibre TEXT` (free-form plant codes), `water_absorption_pct NUMERIC(5,2)`, `pei_rating SMALLINT` (0-5), `edge_type TEXT` (rectified/non_rectified), `surface_texture TEXT` (list `product.surfaceTexture`), `application TEXT` (floor/wall/floor_wall/outdoor), `origin_plant TEXT` (list `product.originPlant`). Option-list-backed values are plain TEXT on `products`, exactly as `product_type` already is.

`inventory_stock`: `min_stock_level`, `max_stock_level NUMERIC(12,2)`. **Reorder point already exists** as `reorder_level`; renaming it would churn `countLowStock` (inventory.repository.ts:304-323), `mapStockLevel` (mappers.ts:572-596), the route and the mutation kind for zero behaviour change.

`stock_movements`: `batch_no`, `shade`, `calibre`, indexed on `(tenant_id, product_id, batch_no)`.

**4.1 Batch/lot is not a product column.** One product receives many lots; a column would be false the second inbound. True lot-level on-hand requires re-keying `inventory_stock` from `(tenant_id, product_id, colour)` through `stock_reservations`, `line_item_quantities`, `reservedTotals`, `countLowStock`, dispatch settlement and the document renderer — a workstream, not a column. What ships instead answers "which lot is this" from the movement ledger, and is the data that upgrade would start from.

**4.2 Purchase rate is more sensitive than sale rate.** Two capabilities in permissions.ts, group `pricing`, both `MINIMUM_TIER: 'management'` (safe against the tier ceiling by construction: any role holding `field.saleRate.edit` is already management-or-above, permissions.ts:220), added to `FIELD_PERMISSIONS`.

```ts
export interface ProductVisibility { rates: boolean; cost: boolean }
export function maskProduct(product: Product, visible: ProductVisibility): Product
export function withPermittedPurchaseRate<T extends { purchaseRate?: number | null }>(draft: T, allowed: boolean): T
```
Call sites: catalog.service.ts:253, :269, :317, :361 with `{ rates: canSeeRates(actor), cost: canSeeCost(actor) }` (`canSeeCost`/`canEditCost` beside master/src/domain/visibility.ts:26/:43); office/src/http/app.ts:1024 and :1047.

**The signature change is not sufficient on its own.** office `maskChangeEvent` opens with `const allowed = …includes('field.saleRate.view'); if (allowed) return event;` before the switch. That guard is not a call site and keeps compiling, leaking `purchaseRate` to every Office user holding sale-rate view. It must become `if (vis.rates && vis.cost) return event;` with the switch passing `vis` to `maskProduct` and `vis.rates` to the lead/order/variant branches. `forCurrentUser` has no such short-circuit and needs only the object. `SNAPSHOT_POLICY` does not help here — it is keyed on collections, and `products` is already `'mask-rates'`.

Accepted and stated: backup-export dumps `purchase_rate` unmasked, exactly as it already does `rate`; that path is gated at the storage-admin tier.

### 6. Not doing, and why

Lot-level on-hand inventory (§4.1). Batch as a product column — a deliberate refusal of the requirement as literally written, replaced with the correct model. A product-level default min/max that new colour rows inherit — speculative. Backfilling ceramic columns from `parameters` — no fixed vocabulary, so any mapping mislabels. Recovering already-damaged rows — impossible from the activity log; only a backup or an Office snapshot holds the old values, and this adds no recovery tool for a bug that, on the evidence, has never fired on a shipped installation. A UI for the new attributes, including the office's existing ProductDetail (office/web/src/screens/ProductDetail.tsx:116-130), which keeps showing its five fields until D. Renaming `reorder_level`. A `field.mrp.view` permission. Migrating the two forked panel `strings.ts` dictionaries.

### 7. Risks

The merge path has no validation layer; every column added to it is a new way for offline work to be permanently rejected — §2.3 is the mitigation and is not optional. Stamping clocks switches the merge engine back on, so conflict rows will appear where none did; a panel must **reconnect once** after the Master upgrade before its `baseFieldHlc` means anything, and edits queued across that boundary produce one conflict row per changed field. The partial patch changes the meaning of an omitted key — requirement 13's REST client must be documented against absent-means-untouched. `purchaseRate` is optional and masked by absence: any `product.purchaseRate ?? 0` treats "may not see cost" as "cost is zero", so margin arithmetic is server-side only. `uom NOT NULL DEFAULT 'box'` asserts a unit for every existing row; any later cross-product quantity sum must branch on it.
