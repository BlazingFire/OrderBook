## Corrected design

## J — External API in both directions: a keyed public REST API on the Master, and a generic outbound REST connector with a field-mapping UI

**Verdict.** Inbound, `/api/v1` is a versioned router that reuses the existing *services* (never the browser routes) and authenticates a key that is its own principal for audit (`actor_type='api_key'`, `actor_id=<key uuid>`, both inside the hash chain) but bound to an owner user for authority (permissions = owner's role ∩ key scopes; party scope is the owner's, from `resolvePartyScope`). Outbound, a connector is pure data — base URL, auth kind, JSON-pointer field maps, a schedule — so "Hermes" is a JSON profile, not a code path, and every write goes through `catalogService`/`inventoryService` so validation, masking, party access, `publishChange` and the audit trail hold with one implementation.

### 0. Security posture

`master/src/config/index.ts:44` binds `0.0.0.0:4100`. Everything on the shop LAN already reaches every Master route; the gates are the session cookie and `publicUpdateRoutes` (`update.routes.ts:34-59`), which streams a 100–200 MB installer unauthenticated. A keyed API opens no new port — it adds a second credential type on an already-exposed socket. The new risk is a bearer token on another machine's disk with **no TLS anywhere in this product**. Mitigations: off by default; per-key scopes; `expires_at`; one-click revoke; and the structural guarantee that a key never exceeds its owner. Not designed in: TLS. Self-signed certs on shop PCs plus an Electron trust-store entry is a support burden out of proportion to a ten-metre LAN. That is the honest cost.

**There is no per-key party pinning.** A key's party scope is its owner's, full stop. `party_access` plus `owner_user_id` already expresses "this key sees these parties" through the one grant surface administrators maintain; a second surface would have to be widened through `applyPartyScope`, `partyScopeSql`, `partyScopeLogSql` **and** `party-access.service.ts:256 levelForParty` (whose `if (scope.seesAll) return 'manage'` shortcut, plus `party-scope.ts:67 levelFor`'s "unassigned is open to everyone" rule, is where every write gate actually lands). Miss that fourth site and a pinned key edits any unassigned party. Narrow keys are made by owning them from a narrow user.

### 1. Schema — one migration

`master/src/db/migrations/20260314000000_public_api_and_connectors.ts`, imported in `index.ts` and placed in the array after `20260313000000_party_access` and **before** the pinned `20260309000000_new_module_permission_grant`, so both the ascending-order and deliberately-last assertions in `migration-registry.test.ts` hold. `20260314` is the next free slot (`20260312` and `20260313` are each used twice, which that test explicitly permits). Add the name to `SHIPPED` only once it reaches a real installation, and never remove it.

Tables: `api_keys` (id, tenant_id, label, `token_prefix` unique, `token_hash`, `owner_user_id`, `rate_limit_per_min` default 120, `expires_at`, `revoked_at`, `last_used_at`, `created_by_user_id`, timestamps); `api_key_scopes` (tenant_id, api_key_id, permission); `api_connectors` (tenant_id, slug, label, `base_url`, `auth_kind` in none|header|bearer|basic, `auth_header`, `auth_username`, **`credential_ref`** — a key *into* workstream F's secret store, never a secret — `direction`, `schedule_kind` in manual|on_change|periodic, `interval_min >= 5`, `run_as_user_id`, `mapping_version`, `profile_slug`, `is_enabled` default false, `last_run_at`/`last_status`/`last_error`); `api_connector_resources` (tenant_id, connector_id, entity in party|product|order, remote path/method, `items_pointer`, `remote_id_pointer`, `updated_at_pointer`, paging params, `watermark`, unique per (connector, entity)); `api_connector_field_maps` (tenant_id, resource_id, `local_field`, `remote_pointer`, `transform`, `on_conflict` in remote_wins|local_wins|flag, `is_required`); `api_connector_links` (connector_id, tenant_id, entity, remote_id, `local_id` with no FK, `remote_hash`, `last_seen_at`); `api_connector_runs` (BIGSERIAL, tenant_id, connector_id, mode, trigger, mapping_version, timings, status, counts, `errors` JSONB).

### 2. Key issuance

`master/src/services/api-key.service.ts`: `issueKey`, `revokeKey`, `listKeys`, `digest`. Token wire form `obk_<12-char prefix>_<32-byte secret>`; `token_prefix` is the indexed lookup handle and is displayed, so no fingerprint column is needed — it does what `panel-credential.repository.ts:42 credentialFingerprint` does for panels.

**sha256, not scrypt.** `password.ts` uses scrypt (~40 ms) for human-chosen secrets; an API key is 256 bits of machine entropy verified on every request, and scrypt would cap the API near 25 req/s on one core. Store the digest, compare with `timingSafeEqual`. Plaintext is returned once, mirroring `OneTimeSecret` (`inputs.ts:305-317`) and the "recovery is a reset" rule at `access.routes.ts:123-126`. `shared/src/domain/api-keys.ts` declares `ApiKey` without `token`/`tokenHash`; `mapApiKey` destructures both away, and `credential-invariants.test.ts` is extended to police it in its existing source-reading style. Requirement 6 must not sweep this up — a key digest is one-way.

### 3. Authentication

`master/src/http/middleware/require-api-key.ts`. Read `Authorization: Bearer obk_…` or `X-OrderBook-Key`; parse prefix; one indexed `findByPrefix`; `timingSafeEqual`; reject revoked/expired. Then `permissionSetForRole(tenantId, owner.roleId)` and `effectivePermissions(role.permissions.filter(p => keyScopes.has(p)), role.tier)` — intersection, never union, with the tier ceiling re-applied. It **never** falls back to `req.user`; `attachSession` runs app-wide but resolves nothing for a cookieless request.

Cost, stated honestly: two indexed queries per request. `permissionSetForRole` (`role.repository.ts:107-147`) always issues a `roles` SELECT to read `version` before consulting its cache — it is not free.

Actor: `{ tenantId, actorType: 'api_key', actorId: key.id, userId: key.ownerUserId, permissions: scoped, deviceCode: \`API:${key.tokenPrefix}\`, actorName: \`${owner.displayName} via API key ${key.label}\` }`. Own principal for audit because `activity_log_row_hash` (`20260310:78-97`) covers `actor_type` and `actor_id` but **not** `actor_name`; bound to a user for authority because `party_access` is keyed on `user_id` and `party-scope.ts:53 resolvePartyScope` reads `actorUserId(actor)`. `ActorContext.actorType` and `activity-log.repository.ts:42 ActorType` and `shared/src/domain/activity.ts:15 ActivityActorType` all widen with `'api_key' | 'connector'`; no field is added, so the ten existing actor literals and `fixtures.ts:254` are untouched.

### 4. The endpoint surface

Mounted in `app.ts` after `/api/health` and before `app.use('/api', dataRoutes)` (line 64), whose `dataRoutes.use(requireAuth)` would otherwise 401 a cookieless key. **When `api_enabled` is false the v1 router answers 404 itself and never calls `next()`** — `next()` would fall into `dataRoutes` and produce a 401, and the SPA catch-all `/^(?!\/api).*/` never matches an `/api` path.

A separate versioned namespace over the same services, not the browser handlers: `dataRoutes` takes a cookie, its `paging()` accepts the UI's `scope=assigned`, and its shapes carry no compatibility promise. `paging()` moves from `data.routes.ts:56` to `master/src/http/query.ts` and is imported by both, not copied.

`master/src/http/public-api-contract.ts` (**in `master`, not `shared`** — `shared/src/index.ts` is a flat `export *` barrel that both offline browser bundles consume, and both consumers of this table are in `master`) holds `PUBLIC_API_ROUTES`. `public-api.routes.ts` builds the router by iterating it against `Record<operationId, PublicApiHandler>`, so a missing handler or an unregistered handler is a compile error — the same tripwire shape as `office/src/http/app.ts`'s `Record<keyof SyncSnapshot, SnapshotPolicy>`.

Routes: `GET /openapi.json`, `GET /whoami`; parties and products `GET`/`POST`/`GET :id`/`PATCH :id`; `GET /stock`, `POST /stock/inbound` (`inventory.edit`), `POST /stock/adjust` (`stock.adjust`); `GET /leads`, `GET /leads/:id`; `GET /orders`, `GET /orders/:id`, `PATCH /orders/:id`, `POST /orders/:id/stage`; `GET /search` → `searchService.search`; `GET /events` → `logService.listLogs`. Absent: `POST /leads` (`data.routes.ts:6-8` makes "the Master cannot create a lead" structural), all `DELETE`, and users/roles/panels/documents/storage.

**PATCH is read-merge-write, and the read is unmasked.** `catalogService.updateProduct`/`updateParty` are full replaces — `product.repository.ts:323-346 columnsFrom()` writes every column `?? null` and `party.repository.ts:252-267` is identical — and they throw `validation.product.nameRequired`/`codeRequired` on an absent name or code, so a two-field PATCH cannot reach the repository at all. Merge against `productRepo.findProductById` / `partyRepo.findPartyById` (unscoped repository reads, already used at `catalog.service.ts:131` and `:365`), **never** against a masked service read: `visibility.ts:29-33 maskProduct` removes `rate` by key absence, `withPermittedRate` then leaves it `undefined`, and `columnsFrom` writes `null` — silently zeroing the price. A PATCH body naming a field the key cannot see is refused 403. The whole inbound-write surface is gated on the `columnsFrom` patch-semantics fix landing first.

Masking on reads is free: every handler calls a service that already applies `maskProduct`/`maskVariant`/`withPermittedRate`, so a key without `field.saleRate.view` receives `rate` absent, not null.

**Events feed, not webhooks.** `activity_log` is already append-only, monotonic, keyset-paged, party-scoped and permission-gated with a hash chain, and `logService.listLogs:46` already returns `CursorPage`. `GET /events?cursor=&limit=` wraps it behind `logs.view`. Entries name what changed, so the consumer follows with a `GET` that re-applies masking — a pushed payload would not.

**Rate limiting**, no dependency: fixed 60 s window in a `Map<keyId, {start,count}>`, 429 with `Retry-After`, `TooManyRequestsError extends AppError` (429, `rate_limited`, key `error.rateLimited`). No sweep — the map is keyed by key id and is bounded by the number of issued keys, unlike `auth.service.ts:48 failures` which is keyed by attempted username. `last_used_at` is flushed from the connector scheduler's 60 s tick, not per request. The EN string uses a `{seconds}` placeholder: `shared/tests/i18n-coverage.test.ts` fails any string containing three consecutive digits.

**No CORS headers, cookies ignored.** `hub.ts:86`'s `cors: { origin: true, credentials: true }` is a pre-existing cross-site-WebSocket-hijack hole; this workstream must not extend it. (Closed on 2026-09-24, outside this plan: the hub has no CORS option now and refuses a cross-site handshake, `master/src/realtime/socket-origin.ts`.)

**Failed key auth is not written to `activity_log`** — every insert takes `pg_advisory_xact_lock(hashtext(tenant_id))` (`20260310:104`), so key-spraying would serialise every audited write in the company. Failures go to an in-memory counter and the process log.

### 5. The outbound connector

`connector-run.service.ts`: `testConnection` and `runConnector`. Node 22 global `fetch` + `AbortSignal.timeout(10_000)` — no HTTP client dependency. `master/src/domain/json-pointer.ts` (`readPointer`, `flattenPointers`) and `master/src/domain/connector-mapping.ts` (pure: apply map + transform, produce the local input and its sha256 of key-sorted JSON) are the only new logic, both unit-testable with no database.

**SSRF guard: require `http:`/`https:`, reject only the Master's own origin** (any local address on `config.http.port`) so a connector cannot recurse into `/api/v1`. Loopback and private ranges are **allowed** — the shop LAN has no internet and the named target (Miracle/Hermes) runs on the shop PC itself, so blocking `127.0.0.0/8` would make the feature useless.

**Connection test is schema discovery**: fetch one page, return `samplePointers` (flattened pointers of item zero) — that is what the mapping UI's remote-field picker renders.

**Dry run enforced before first import.** Any field-map write bumps `mapping_version`; a real import is refused unless a successful dry run exists at the current version. Dry run returns per row `{remoteId, action, localId, changes[], error?}` and writes only its `api_connector_runs` row.

**Writes go through services, never SQL** — `catalogService.createParty/updateParty/createProduct/updateProduct`, `inventoryService.recordInbound` — with the same unmasked read-merge as PATCH. Actor: `actorType: 'connector'`, `actorId: connector.id`, `userId: run_as_user_id`, permissions from that user's role. `systemActor` is unusable: its `permissions` is `null`, so `requirePermission` refuses everything.

**Change fan-out must be debounced first.** `hub.ts:129-136,168` calls `broadcastDashboard(io)` on every `product`/`party`/`lead`/`order`/`stock`/`sync_conflict` change with no debounce, and `broadcastDashboard` (`hub.ts:846-886`) runs `resolveSession` + `permissionSetForRole` + a full dashboard aggregate **per admin socket, per event**. A 500-row import would fire 500 of those per admin. The fix is a trailing debounce (~500 ms) around `broadcastDashboard` inside `hub.ts` — the shared function, so sync flushes and bulk operations benefit too.

**Conflicts reuse the store, not the clock.** A remote `updated_at` is not causally ordered with our HLC, so `mergeUpdate` (`sync.service.ts:356-434`) would pick winners arbitrarily. Each mapped field carries `on_conflict`: `remote_wins`, `local_wins`, or `flag` — which writes nothing and records a row via `syncRepo.recordConflicts` (`sync.repository.ts:68`) with `losing_device_code = 'CONN:<slug>'`, `winning_device_code = 'MASTER'`, `losing_hlc = await nextHlc(trx)`. It then appears on the existing Conflicts screen behind `sync.resolveConflicts`. `flag` is offered **only** for the fields `conflict.service.ts:24-44 COLUMNS` can restore: `party.name/phone/notes/customFields` and `product.name/alias/rate/customFields`.

**Idempotency, two layers**: `api_connector_links` turns a re-import into an update; `remote_hash` turns an unchanged row into a zero-write skip, which also closes the `on_change` echo loop (`DataChangedEvent` carries no actor, so a hash is the only available loop guard).

**Partial failure is the default** — one transaction per row (each service call opens its own), status `'partial'`, `errors` capped at 50 plus a total. **Retry** network errors and 429/502/503/504 three times at 1 s / 4 s / 16 s; other 4xx do not retry. No dead-letter queue: `watermark` only advances on success.

**Scheduling: one 60 s `setInterval`** in `connector-scheduler.ts`, started beside the session sweep (`index.ts:120`) and cleared in `installShutdownHandlers` (whose `resources` interface widens by one field). Module-level `Set<connectorId>` prevents overlap; minimum interval 5 minutes; `on_change` subscribes to `change-bus.ts:23 onChange` with a 5 s debounce; boot marks any run left `'running'` over 30 minutes as `'failed'`. `// ponytail: single-process scheduler, no cross-restart resume; a job table if a second Master ever exists.`

**Secrets go through workstream F** (`readSecret`/`writeSecret`, key `connector.<id>.credential`). If F has not landed, the connector form refuses to save a credential and stays disabled — never a plaintext column. `auth_kind='none'` works regardless. Connector responses never carry the credential and run errors never echo request headers.

**"Hermes" is data**: `connector-profiles.ts` exports a frozen `ConnectorProfile` array; "create from profile" inserts rows. The same shape imports/exports as JSON at runtime, so a new app needs a file, not a build.

### 7. The Office Panel: nothing, both directions

**Inbound**: Office binds `127.0.0.1` (`office/src/config/index.ts:94`), so an API there is unreachable by the machines that want it; an integration on an office PC calls the Master over the LAN with a key. **Outbound**: connectors run only on the Master. Office has no direct database, its writes are outbox-queued, and it can resolve neither `api_connector_links` nor `sync_conflicts`. No connector UI and no forwarded socket command — that would mean a new `ClientToServerEvents` entry and an Office forwarding path for a screen nobody at an office desk can act on. No `SyncSnapshot` collection is added, so `SNAPSHOT_POLICY` is untouched.

### Risks

No TLS and the Master binds `0.0.0.0` — a key is as confidential as the existing session cookie, which is to say not at all against a passive LAN sniffer. `product.repository.ts:323-346` / `party.repository.ts:252-267` full replace is a **hard blocker** for every write path here. `catalog.service.ts` passes `fieldHlc: {}` at **four** online write sites (create/update party, create/update product), emptying the per-field clock the sync merge depends on — a connector makes that more frequent on a shop that also runs offline panels. `hub.ts:86` `cors: origin:true` with credentials remains a hole this workstream does not extend but does not close. (Closed on 2026-09-24, outside this plan: the hub has no CORS option now and refuses a cross-site handshake, `master/src/realtime/socket-origin.ts`.) A `party` conflict raised by a `flag` mapping is visible to every `sync.resolveConflicts` holder — `sync.repository.ts listConflicts` narrows only `lead`/`order` by party scope. Rate-limit windows are per-process and reset on restart. `api_connector_links.local_id` has no FK; a link whose target is gone is treated as a create, which is intended and must be tested.

### Not doing

No outbound webhooks (the events feed is the same thing, correctly scoped, for free). No TLS, no OAuth2/JWT. No per-key party pinning — see §0. No deep per-field JSON Schema in the OpenAPI document; the route table, permissions and parameters cannot drift, and bodies name their TypeScript type. No `DELETE` routes, no users/roles/panels/documents/storage endpoints, no `POST /leads`. No API surface or connector UI on the Office Panel. No job queue or cross-restart resume for runs. No API-key fingerprint column — `token_prefix` already answers that question.
