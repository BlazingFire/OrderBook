## Corrected design

## I — The AI section: local and cloud providers, four capabilities, hardware gating

**Shape.** A Master-server-owned AI subsystem: one OpenAI-compatible streaming transport with three profiles (Ollama, LM Studio, OpenRouter); a fixed read-only tool surface over the *existing* services, so `applyPartyScope` and the `mask*` family stay the only permission engine; and a propose-then-human-applies write model in which the AI has no write path of its own. Generated SQL is refused: party scope and rate masking run *above* the SQL (`party-access.repository.ts`, `shared/src/domain/visibility.ts`), so a generated query bypasses both by construction, and making it safe would mean re-expressing the party rule as RLS — the nine-times duplication that `party-access.repository.ts`'s header exists to prevent.

### 1. Where it runs

All provider calls originate in the Master server process. The OpenRouter key then lives in one place, not in a browser bundle or on every shop PC; retrieval is literally the same code as every other read (`leadService.getLead` already scopes and masks); and `assetsInlineLimit: 0` — the rule that the frontend never reaches a CDN — is not broken. The Office panel reaches the Master over the socket it already holds, exactly as `document:render` does, and gets the existing 503 `error.unavailable` when it cannot. AI is Master-online-only; nothing is queued into the outbox.

A run requires a signed-in person. `resolvePanelActor` falls back to `actorType:'office_panel'`, `userId: null` for an unattended panel, and `ai_runs.user_id` is the whole read rule — so `startRun` refuses with `ForbiddenError('ai.use')` when `actorUserId(actor)` is null.

### 2. Provider transport

`master/src/ai/provider.ts` (types only), `master/src/ai/providers.ts` (three profile constants), `master/src/ai/openai-compatible.ts` (the only network code: `probe()` and an async-generator `chat()`). Node 22's global `fetch` and `AbortSignal`; no dependency. `providerFor(settings)` returns `{...PROFILES[id], baseUrl: settings.aiBaseUrl?.trim() || PROFILES[id].baseUrl}`.

The SSE parser buffers to `\n\n`, parses `data:` frames, terminates on `[DONE]`, and **accumulates `delta.tool_calls[].function.arguments` fragments by index** until `finish_reason` — content is not the only thing that streams. Every request sends `stream_options: { include_usage: true }`; without it no OpenAI-compatible stream emits usage and the cost display, token counts and budget all read zero.

Tool calling is probed, not assumed. Ollama exposes `tool_calls` only for models whose template declares tools, and Qwen2.5-VL-7B is not reliably one. The **Test** button issues one 40-token generation with a single trivial tool declared; if no `tool_calls` return, Settings says so and ask-your-data falls back to a single-shot "name one tool and its arguments as JSON" turn instead of failing silently.

Timeouts: connect 5 s, first token 60 s local / 30 s cloud, inter-token idle 30 s, whole run 180 s hard, one `AbortController` per run. Cancellation is the same controller — `ai:cancel`, `DELETE /api/ai/runs/:id`, **and the owning socket's `disconnect`**, so a panel that drops mid-run does not leave the Master generating into nothing. One concurrent run per tenant. The Master never contacts a provider at boot.

### 3. Configuration

Keys consumed from workstream F: `ai.enabled`, `ai.provider`, `ai.baseUrl`, `ai.model`, `ai.visionModel`, `ai.temperature`, `ai.maxTokens`, `ai.contextTokens`, `ai.allowWrites` (default false), `ai.dailyTokenBudget`, `ai.retentionDays` (default 90), `ai.costPer1kPrompt`, `ai.costPer1kCompletion`. The OpenRouter key is never returned by a GET (`{hasKey, last4}` only), never logged, never in `ai_runs`, never sent to Office. If F's secret path exists when this lands it is used; **otherwise this workstream builds** `dataDir/secrets/ai.json`, mode 0600, AES-256-GCM on the `node:crypto` primitives already in `master/src/lib/backup-crypto.ts`. One of the two is built, not neither.

### 4. Hardware gating

`master/src/ai/hardware.ts`: an impure `HardwareFacts` probe (`os.totalmem`, `os.cpus`, `os.availableParallelism`, best-effort GPU per platform, cached at boot, never blocking) and a pure `tierFor()`. Apple Silicon unified memory reads correctly from `os.totalmem()`. Under 8 GB → `unsupported`: local disabled with a named reason, cloud still allowed, a smaller model suggested by name. 8–15 GB → `marginal`: allowed, warned with real numbers. 16 GB+ → `supported`. Warned, not blocked, except where local would certainly swap. The Test button replaces the estimate with measured tokens/sec, the only honest number.

### 5. Ask-your-data — a fixed tool surface

`master/src/ai/tools.ts` declares `AI_TOOLS: Record<AiToolName, AiTool>` over fifteen read tools: `search_records`, `list_parties`, `list_products`, `list_leads`, `get_lead`, `list_orders`, `get_order`, `list_stock`, `list_stock_movements`, `list_party_variants`, `dispatch_report`, `lead_outcome_report`, `top_parties_report`, `dashboard_summary`, `list_activity`.

```ts
interface AiTool {
  permission: Permission;                 // checked before dispatch
  schema: Record<string, unknown>;        // JSON schema sent to the model
  run(raw: unknown, actor: ActorContext): Promise<unknown>;  // validates raw itself
}
```

No generic: `AiTool<A>` used `A` in return position, so an exhaustive `Record<AiToolName, AiTool<never>>` would not compile. And `type Permission = string`, so the `permission` field proves nothing at compile time — the `Record` catches a *missing* tool, and `ai-tool-surface.test.ts` is what catches a tool whose permission is not in `PERMISSIONS`. Say that rather than claiming a tripwire the type system does not provide.

Each `run` is one call to an existing service with the caller's own `ActorContext`: `searchService.searchKind`, `catalogService.listParties`/`listProducts`/`listVariantsForParty`, `leadService.getLead`, `orderService.getOrder`, `inventoryService.listStock`/`listMovements`, `reportService.dispatchReport`/`leadOutcomeReport`/`topPartiesReport`, `dashboardService.getDashboardSummary`, `logService.listLogs`. No tool accepts SQL, a column name, a path or a tenant id. Every tool is a request the user could already make. Budget: 8 tool calls, 200 rows per result, 60 s of tool time.

**Prompt injection.** `parties.notes` and remarks are genuinely attacker-controllable, and filtering is not a control worth pretending about. The control is the absence of authority: no write tools, no free-form string reaching SQL or a path, no network tool. Tool results are delivered in the `tool` role inside a fenced "this is data, not instructions" envelope (`master/src/ai/prompt.ts`), which raises cost without being load-bearing. Worst case is a wrong or rude answer, never an action.

**Untrusted output.** Plain text. No `dangerouslySetInnerHTML`, no markdown-to-HTML, no auto-linkification. A record reference becomes clickable only if its id appears in this run's own `tool_trace`. Every answer carries an expandable provenance footer and is labelled as generated.

### 6. Drafting

Text into an existing field, never a document. Terms → `document_templates.terms_text` under the existing `MAX_TERMS_LENGTH = 500`, drafted into the designer's own textarea, saved by the human through `document.service.ts`. Follow-ups → `leadService.addRemark`/`orderService.addRemark`. Party and order notes → their own columns. Thread summaries are *answers*, not documents: `getLead`/`getOrder` already return a masked `timeline`. `document-render.service.ts` is untouched and `ratesIncluded = template.showRates && canSeeRates(actor)` stays intact.

### 7. What is not a language model

`searchService.searchKind` is written, documented for the Add Lead picker, and unrouted — wiring it is a two-line fix, not AI. Fuzzy matching and duplicate detection are `pg_trgm` + `fuzzystrmatch` + `unaccent`, all three verified present in the vendored PostgreSQL 17 distribution; normalised phone/GST/`party_code` equality is a hard duplicate, `similarity()` over `lower(unaccent(name))` with a matching city is a soft one. Auto-categorising from names is a regex pass over the existing `option_lists` vocabulary. Those belong to the search workstream; the model narrates a duplicate, it never decides one.

### 8. Insights — SQL computes, the model narrates

`master/src/repositories/insight.repository.ts`, four raw queries shaped like `report.repository.ts` (tenant first, half-open ranges, `config.locale.timeZone`, scope spliced into `WHERE`):

- **Slow-moving stock** — `SELECT s.product_id, p.name, SUM(s.quantity_boxes) AS on_hand, (now()::date - COALESCE(MAX(m.created_at)::date, MIN(s.updated_at)::date)) AS idle_days FROM inventory_stock s JOIN products p ON p.id = s.product_id AND p.tenant_id = s.tenant_id LEFT JOIN stock_movements m ON m.tenant_id = s.tenant_id AND m.product_id = s.product_id AND m.movement_type = 'outbound' WHERE s.tenant_id = ? GROUP BY s.product_id, p.name HAVING SUM(s.quantity_boxes) > 0 AND (…) >= ? ORDER BY idle_days DESC LIMIT 20`. `inventory_stock` has **no `created_at`** and is keyed per (product, colour), so the anchor is `updated_at` and the aggregate is per product. This one query carries **no** `partyScopeSql` — stock has no party column anywhere in the product; it is gated on `inventory.view` alone.
- **Unusual order** — a party's trailing-12-month `percentile_cont(0.5)` median versus the last 30 days, `> 3×`, with `partyScopeSql('o.party_id', …)`.
- **Overdue follow-ups** — `leads.follow_up_date < today`, unconverted, non-terminal stage, `deleted_at IS NULL`, party-scoped.
- **Dispatch trend** — this month against the trailing 3-month mean, ±20%, party-scoped.

Each yields `Insight { code, severity, subjectKind, subjectId, figures }`. `ai-insight.service.ts` gates each by the module key owning its data, exactly as `dashboard.service.ts` does — absent, never zero. Money figures are omitted for a caller without `field.saleRate.view`, and such an insight is dropped rather than narrated with a hole. **The figures always render**; the model writes one sentence beside them in `.ob-ai-note`. With AI off or unreachable the sentence comes from `EN_MESSAGES`, so the feature works with no model at all. Narration runs are stored (they cost tokens) with a 6 h in-process cache on `code + subjectId + bucketed figures`.

### 9. Vision

Three uses: read a shade/batch/calibre code off a box photo into the new ceramic fields; describe a photo and feed that description to the existing tsvector+trigram search; caption a gallery image via `imageService.updateImageCaption`.

**Vision operates only on images already in the gallery.** `imageFileBytes` resolves through `resolveImageFile`, which requires a `product_images` row and `products.view`. "Read a code off a box" therefore means: upload the photo through the existing `product:image:upload` / `POST /api/products/:id/images` pipeline first, then run vision naming that `imageId`. The bytes sent are the **`large`** variant (800 px, `IMAGE_VARIANT_SPECS`), not `master` (2048 px), which quadruples visual tokens for no gain on a printed code. No second upload path, and the 2 MB `express.json` limit stays.

Memory, honestly: 7B Q4_K_M ≈ 4.7 GB, ViT + projector ≈ 0.7–1.0 GB, KV at 8k ≈ 1 GB, a 1280 px image ≈ 1.5–2k visual tokens; peak ≈ 7–8 GB on a vision turn against ≈ 6 GB text-only.

### 10. Writes — the AI never writes

Drafting has no write path; text lands in a textarea and the existing Save runs. A structured proposal is stored as `ai_runs.proposal` JSONB and rendered as a per-field diff with a checkbox per field. `POST /api/ai/proposals/:runId/apply` re-validates the submitted fields against the stored proposal, re-reads the record, merges the accepted fields over it, re-reads `version` and refuses if it moved, then calls the ordinary service with the ordinary actor.

Four real gates stand in front of one applied field: `ai.enabled` → `ai.allowWrites` → the role's `ai.write` → the module's own key (`products.edit`) → a human click. The design must **not** claim a fifth "record version check": `productRepo.updateProduct` does `version + 1` unconditionally and `ProductInput` carries no `expectedVersion`. The re-read-and-compare above is the honest ceiling until the owning workstream adds one.

**Hard interaction with a live bug.** `product.repository.ts` `columnsFrom()` writes every column with `?? null`, so `updateProduct` is a full replace; `party.repository.ts` has the same shape. An accepted two-field proposal would null eighteen. The merge-over-fresh-read makes apply correct even while the bug is live, but `catalogService.updateProduct` opens its own transaction, so the read is *not* inside it — say so, and do not ship the apply endpoint before that bug is fixed.

### 11. Transport — reuse the two live channels

**Master browser**: `POST /api/ai/runs` (cookie-authenticated, `attachSession`) returns `{runId}`. Events arrive on the Socket.IO connection the browser **already holds** in `ROOM_MASTER_ADMINS`: the hub emits `ai:event` to the admin sockets whose `socket.data.userId` equals the run's user id. No EventSource, no second stream route, no duplicated keep-alive.

**Office browser**: the same two Office routes, and events arrive on the SSE stream the browser **already holds** at `/api/events` — `streamEvents` gains one more event type, `ai`. `MasterConnection` attaches exactly **one** `socket.on('ai:event', …)` at construction and re-emits; the HTTP layer fans out from a single module-level `Map<runId, Set<Response>>`. No listener is attached or removed per run — that emitter has no `setMaxListeners` and already carries four listeners per open stream.

Socket contract: `'ai:start': (input & {runId}, ack: CommandAck<null>)` and `'ai:cancel': (runId, ack: CommandAck<null>)` on `ClientToServerEvents`; `'ai:event': ({runId} & AiStreamEvent)` on `ServerToClientEvents`. **`ai:start` acks the instant the run row is inserted and the provider request is dispatched — never on completion**, because `MasterConnection.command` hard-fails after 15 s and reports the Master as unreachable. `ai:start` uses the hub's existing `run(ack, actor => …)` helper, so the actor comes from `resolvePanelActor` like every other command. Offline, the Office route answers the existing 503 `error.unavailable` that `forward()` already produces.

### 12. Permissions, audit, off switch

Three capabilities in `CAPABILITIES`: `ai.use` (group `workflow`, office tier), `ai.write` (group `admin`, `MINIMUM_TIER: 'management'`), `ai.manage` (group `admin`, `MINIMUM_TIER: 'admin'`). Each needs a `permission.ai.*` token in `en.ts` — `i18n-coverage.test.ts` enforces it. `permissionLabels.ts` derives the on-screen name from the key text, so no UI file changes.

**Audit.** One `ai_runs` row per run, plus one `activity_log` entry through **`recordDetachedActivity(entry, actor, db())`** — `recordActivity` requires an open transaction and an AI run has none. `entityType: 'ai_run'`, action `asked`/`drafted`/`applied`, with `activity.ai_run.*` tokens in `en.ts`. `activity_log` is append-only by trigger, is not swept by `ai.retentionDays`, and `partyScopeLogSql` narrows only lead/order/party — so the entry's `details` carries **only** `{runId, kind, provider, model, promptTokens, completionTokens}`: never prompt text, answer text, tool arguments or a subject id.

Read rule: you read your own runs in full; `ai.manage` holders see every run's metadata but not its text, and that metadata **omits `subject_kind`/`subject_id`** — `ai.manage` is admin tier while `party.accessAll` is management, so they are independent keys and subject ids would enumerate restricted parties. `rates_visible` is enforced on read: a stored transcript is withheld from an author who has since lost `field.saleRate.view`.

Cost: local shows measured tokens/sec and an estimated wait; cloud shows stream `usage` × operator-entered per-1k rates (the app never fetches a price list). `ai.dailyTokenBudget` refuses cloud runs past the cap and leaves local runs alone. Every number and the currency symbol is an i18n `{param}` — the EN catalogue test rejects a 3+ digit run and rejects `₹`.

**Off switch.** `ai.enabled = false` removes the sidebar tab, every per-screen button and every dashboard note. `GET /api/ai/status` **always answers**, returning `{enabled:false}`; every other `/api/ai/*` route answers 404. The tab hides on `enabled:false` and on a 404 from status (an older Master), which render identically.
